# 36. Explain execution context

An Execution Context is the environment in which JavaScript code is evaluated and executed. It contains information about variables, functions, and the value of this.

### 🧠 Types of Execution Context

1. **Global Execution Context (GEC)**

- Created when your program starts
- Only one exists

👉 Contains:

- Global variables
- Functions
- `this` (global object)

2. **Function Execution Context (FEC)**

- Created every time a function is called

👉 Contains:

- Function arguments
- Local variables
- Inner functions

3. **Eval Execution Context (rare)**

- Created by `eval()` (not commonly used)

### 🔄 Execution Context Lifecycle

Every execution context has **2 phases**:

1. **Creation Phase (Memory Allocation)**

👉 JS engine scans code and sets up memory

- Variables (`var`) → initialized as `undefined`
- Functions → stored completely in memory
- `this` is determined

2. **Execution Phase**

👉 Code runs line by line

- Variables get actual values
- Functions execute

### 🔍 Example

```c
var a = 10;

function test() {
  var b = 20;
  console.log(a + b);
}

test();
```

### 💡 What Happens Internally

**Step 1: Global Execution Context created**

**Creation phase:**

```
a → undefined
test → function
```

**Execution phase:**

```
a = 10
```

**Step 2: Function Execution Context (test)**

**Creation phase:**

```c
b → undefined
```

**Execution phase:**

```c
b = 20
console.log(30)
```

### 📦 Execution Context Components

Each execution context has:

1. **Variable Environment**

- Stores variables & functions

2. **Scope Chain**

- Access to outer scopes

3. **this Binding**

- Depends on how function is called

### 🔗 Call Stack (Execution Stack)

Execution contexts are managed using a stack:

```c
function one() {
  two();
}

function two() {
  console.log("Hello");
}

one();
```

**Stack Flow:**

```
Global → one() → two() → pop → pop
```

👉 LIFO (Last In First Out)

### ⚠️ Key Concepts Connected

- **Hoisting** → happens in creation phase
- **Scope chain** → resolved during execution
- **Closures** → preserve execution context

### 🔥 Interview-Level Answer (Polished)

An execution context is the environment in which JavaScript code runs. It includes variables, function definitions, and the `this` binding. There are global and function execution contexts, and each goes through a creation phase where memory is allocated and variables are hoisted, followed by an execution phase where code is executed line by line. Execution contexts are managed using a call stack.

### 🧩 Visual Mental Model

```c
Call Stack:

| two() |
| one() |
| GEC   |
```

### 🧠 Pro Tip (Interview Gold)

👉 “Execution context explains how JavaScript actually runs your code under the hood.”

# 37. What is lexical environment?

A **Lexical Environment** is a data structure that holds variables and their values, along with a reference to its outer (parent) environment.

### 🧠 Simple Understanding

👉 Think of it as:

```c
{
  variables/functions,
  reference to outer scope
}
```

### 🔍 Where It Exists?

Every execution context has a lexical environment.

So:

- Global execution → Global lexical environment
- Function call → New lexical environment

### ⚙️ Components of Lexical Environment

**1. Environment Record**

- Stores variables and functions

```c
let a = 10;
function test() {}
```

👉 Stored here

**2. Outer Environment Reference**

- Points to parent scope

👉 This creates the scope chain

### 🔗 Example

```c
function outer() {
  let x = 10;

  function inner() {
    console.log(x);
  }

  inner();
}

outer();
```

### 💡 What Happens Internally

**Global Lexical Environment**

```
outer → function
```

**outer() Lexical Environment**

```c
x → 10
inner → function
outerRef → global
```

**inner() Lexical Environment**

```c
(no local variables)
outerRef → outer()
```

👉 When `inner()` runs:

- Looks for x
- Not found locally ❌
- Goes to outer environment ✅

### 🎯 Key Concept: Lexical Scope

Scope is determined by where code is written, not where it's called.

👉 Because of lexical environments

### 🔥 Connection to Closures

```c
function outer() {
  let count = 0;

  return function () {
    count++;
    return count;
  };
}
```

👉 Returned function keeps reference to:

- `outer`’s lexical environment

👉 That’s a closure

### ⚠️ Important Points

- Created at function **definition time**
- Maintains **scope chain**
- Enables **variable lookup**

### 🔥 Interview-Level Answer (Polished)

A lexical environment is a structure that stores variable bindings and a reference to its outer environment. It is created for every execution context and is responsible for maintaining scope and enabling variable resolution through the scope chain. Lexical environments are the foundation of concepts like closures and lexical scoping in JavaScript.

### 🧩 Visual Representation

```
inner → outer → global → null
```

### 🧠 Pro Tip (Interview Gold)

- **Execution Context** = big container
- **Lexical Environment** = part inside it that manages scope

# 38. What is garbage collection?

Garbage Collection (GC) is the automatic process of freeing up memory by removing objects that are no longer reachable in a program.

### 🧠 Why Garbage Collection?

JavaScript:

- Does **automatic memory management**
- Developers don’t manually free memory (unlike C/C++)

👉 GC prevents:

- Memory leaks
- Unused memory consumption

### 🔍 Core Idea

👉 “If something is no longer reachable → it can be removed from memory”

### 📌 What is “Reachable”?

An object is reachable if:

- It’s referenced from:
  - Global variables
  - Current function scope
  - Closure variables

### 🔄 Example

```c
function test() {
  let obj = { name: "Alice" };
}

test();
```

👉 After function ends:

- `obj` is no longer referenced ❌
- GC will clean it up ✅

### ⚙️ How Garbage Collection Works

**1. Mark-and-Sweep Algorithm (Most Important)**
**Step 1: Mark**

- GC starts from root objects (global scope)
- Marks all reachable objects
  **Step 2: Sweep**
- Removes all unmarked (unreachable) objects
  Visual Idea

```
Root → A → B
       ↓
       C

D (not connected) ❌ → will be deleted
```

### ⚠️ Common Memory Leak Scenario

**Closures Holding References**

```c
function outer() {
  let bigData = new Array(1000000).fill("data");

  return function () {
    console.log("Still using it");
  };
}

const fn = outer();
```

👉 `bigData` stays in memory because:

- Closure keeps reference

### ⚠️ Another Example

```c
let obj = { name: "Alice" };

obj = null;
```

👉 Now unreachable → GC will remove it

### 🚀 Advanced Concepts

**Generational Garbage Collection**

- **Young Generation** → new objects
- **Old Generation** → long-lived objects

👉 Most objects die young → optimized cleanup

**Incremental / Concurrent GC**

- Runs in small chunks
- Avoids blocking main thread

### 🎯 Real-World Relevance (Node.js)

- Long-running servers → memory leaks are dangerous
- Common causes:
  - Unclosed DB connections
  - Global caches growing infinitely
  - Event listeners not removed

### 🔥 Interview-Level Answer (Polished)

Garbage collection in JavaScript is an automatic memory management process that identifies and removes objects that are no longer reachable from the root references. It typically uses algorithms like mark-and-sweep to track reachable objects and free memory occupied by unused ones. This helps prevent memory leaks and ensures efficient memory usage in applications.

### 🧩 Bonus Insight

- GC is handled by the JavaScript engine (like V8 in Node.js)
- You cannot manually control it, but you can:
  - Avoid leaks
  - Optimize memory usage

### ⚡ Pro Tips (Interview Gold)

- “Reachability is the key concept”
- Mention mark-and-sweep
- Talk about memory leaks via closures or global variables

# 39. Explain microtask vs macrotask

**Microtasks** and **macrotasks** are two types of task queues in JavaScript’s event loop.
Microtasks **have higher** priority and are executed **before** macrotasks after the current call stack is empty.

### 🧠 Core Idea

👉 Event loop priority:

```
Call Stack → Microtasks → Macrotasks
```

### 🔍 What are Microtasks?

High-priority tasks that run immediately after the current execution completes.

**Examples:**

```c
Promise.then()
Promise.catch()
Promise.finally()
queueMicrotask()
process.nextTick() (Node.js - even higher ⚡)
```

### 🔍 What are Macrotasks?

Lower-priority tasks that run after microtasks are done.

**Examples:**

```c
setTimeout()
setInterval()
setImmediate() (Node.js)
I/O callbacks
```

### 🔄 Execution Order

```c
console.log("Start");

setTimeout(() => console.log("Timeout"), 0);

Promise.resolve().then(() => console.log("Promise"));

console.log("End");
```

✅ **Output:**

```c
Start
End
Promise
Timeout
```

### 💡 Why?

- `Start` → sync
- `End` → sync
- Microtask → `Promise`
- Macrotask → `setTimeout`

### ⚠️ Important Rule

👉 Event loop runs like:

```
1. Execute all synchronous code
2. Run ALL microtasks
3. Run ONE macrotask
4. Repeat
```

### 🔥 Microtask Starvation (Advanced)

```c
function loop() {
  Promise.resolve().then(loop);
}
loop();
```

👉 Infinite microtasks → macrotasks never run ❌

### ⚙️ Node.js Special Case

Priority in Node.js:

```c
process.nextTick() > Promise microtasks > macrotasks
```

👉 `process.nextTick()` runs before everything else

### 🎯 Real-World Understanding

- Promises feel “instant” → microtasks
- Timers feel delayed → macrotasks

### 🔥 Interview-Level Answer (Polished)

In JavaScript, microtasks and macrotasks are two types of queues managed by the event loop. Microtasks, such as promise callbacks, have higher priority and are executed immediately after the current call stack is empty, before any macrotasks like setTimeout or I/O callbacks. The event loop processes all microtasks first and then executes macrotasks one at a time, ensuring efficient handling of asynchronous operations.

### 🧩 Quick Comparison

| Feature   | Microtask         | Macrotask        |
| --------- | ----------------- | ---------------- |
| Priority  | High              | Low              |
| Execution | Before macrotask  | After microtasks |
| Examples  | Promise, nextTick | setTimeout, I/O  |

### 🧠 Pro Tip (Interview Gold)

👉 “Promises always execute before timers—even with 0ms delay.”

# 40. What is currying?

**Currying** is a technique where a function with multiple arguments is transformed into a sequence of functions, each taking one **argument at a time**.

### 🧠 Core Idea

👉 Instead of:

```c
f(a, b, c)
```

👉 You write:

```c
f(a)(b)(c)
```

### 🔍 Basic Example

```c
function add(a) {
  return function (b) {
    return a + b;
  };
}

console.log(add(2)(3)); // 5
```

### 🔥 More Advanced Example

```c
function multiply(a) {
  return function (b) {
    return function (c) {
      return a * b * c;
    };
  };
}

console.log(multiply(2)(3)(4)); // 24
```

### ⚙️ Arrow Function Version

```c
const add = (a) => (b) => a + b;

add(2)(3); // 5
```

### 🎯 Why Use Currying?

**1. Function Reusability**

```c
const add10 = add(10);

add10(5); // 15
add10(20); // 30
```

**2. Partial Application**

👉 Fix some arguments early

**3. Cleaner Functional Code**

- Used in libraries like lodash, Ramda

### 🔄 Currying vs Normal Function

```c
// Normal
function sum(a, b, c) {
  return a + b + c;
}

// Curried
const sum = (a) => (b) => (c) => a + b + c;
```

### ⚠️ Important Note

👉 Currying ≠ partial application (but related)

- **Currying** → one argument at a time
- **Partial** → some arguments fixed

### 🚀 Generic Curry Function (Advanced)

```c
function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) {
      return fn(...args);
    }
    return (...next) => curried(...args, ...next);
  };
}

function sum(a, b, c) {
  return a + b + c;
}

const curriedSum = curry(sum);

curriedSum(1)(2)(3); // 6
curriedSum(1, 2)(3); // 6
```

### 🎯 Real-World Use Cases

- Functional programming
- Event handlers
- Middleware (like Express)
- Reusable utilities

### 🔥 Interview-Level Answer (Polished)

Currying is a functional programming technique where a function that takes multiple arguments is transformed into a series of functions that each take one argument. It enables function reusability, partial application, and cleaner composition of functions, making code more modular and expressive.

### 🧩 Bonus Insight

- Helps in:
  - Function composition
  - Lazy evaluation patterns
- Widely used in advanced JS and FP-heavy codebases

### ⚡ Quick Memory Trick

👉 “One function → multiple functions → one argument each”

# 41. What is function composition?

**Function composition** is a technique where you **combine multiple functions to create a new function**, where the output of one function becomes the input of the next.

### 🧠 Core Idea

👉 Instead of:

```c
f(g(h(x)))
```

👉 You compose them:

```c
compose(f, g, h)(x)
```

### 🔍 Simple Example

```c
const add = (x) => x + 2;
const multiply = (x) => x * 3;

const result = multiply(add(5)); // (5 + 2) * 3 = 21
```

👉 This is basic composition

### ⚙️ Compose Function (Right → Left)

```c
function compose(...fns) {
  return function (value) {
    return fns.reduceRight((acc, fn) => fn(acc), value);
  };
}

const add = (x) => x + 2;
const multiply = (x) => x * 3;

const fn = compose(multiply, add);

console.log(fn(5)); // 21
```

### 🔄 Pipe Function (Left → Right)

```c
function pipe(...fns) {
  return function (value) {
    return fns.reduce((acc, fn) => fn(acc), value);
  };
}

const fn = pipe(add, multiply);

console.log(fn(5)); // 21
```

### 🎯 Why Use Function Composition?

**1. Cleaner Code**

Avoid nested calls:

```c
multiply(add(x)) ❌
pipe(add, multiply)(x) ✅
```

**2. Reusability**

Small functions → reusable building blocks

**3. Better Readability**

Especially with `pipe` (left → right)

### ⚠️ Important Rule

👉 Functions must be:

- **Pure**
- Compatible (output of one = input of next)

### 🔥 Real-World Example

```c
const trim = (str) => str.trim();
const toLower = (str) => str.toLowerCase();
const removeSpaces = (str) => str.replace(/\s+/g, "");

const clean = pipe(trim, toLower, removeSpaces);

clean("  Hello World  "); // "helloworld"
```

### 🔗 Connection with Currying

👉 Composition works best with:

- Curried functions
- Unary functions (one argument)

### 🔥 Interview-Level Answer (Polished)

Function composition is a technique of combining multiple functions into a single function where the output of one function becomes the input of the next. It promotes modular, reusable, and readable code, and is widely used in functional programming patterns.

### 🧩 Quick Comparison

| Concept     | Meaning                                           |
| ----------- | ------------------------------------------------- |
| Currying    | Break function into multiple single-arg functions |
| Composition | Combine multiple functions into one               |

### 🧠 Pro Tip (Interview Gold)

👉 “Compose builds pipelines of transformations”

# 42. What is immutability?

Immutability means that once a value or object is created, it cannot be changed. Instead of modifying it, you create a new copy with the updated value.

### 🧠 Core Idea

👉 “Don’t change existing data → create new data”

### 🔍 Example (Mutable ❌)

```c
let obj = { name: "Alice" };

obj.name = "Bob"; // modifying original object
```

👉 Original object is changed

### ✅ Immutable Approach

```c
const obj = { name: "Alice" };

const newObj = { ...obj, name: "Bob" };

console.log(obj.name);    // Alice
console.log(newObj.name); // Bob
```

👉 Original stays unchanged

### ⚙️ Primitive vs Objects

**Primitives (Immutable by default)**

```c
let a = 10;
a = 20;
```

👉 New value assigned, old one unchanged

**Objects/Arrays (Mutable by default)**

```c
const arr = [1, 2];
arr.push(3); // modifies original ❌
```

**Immutable Array Update**

```c
const newArr = [...arr, 3];
```

### 🎯 Why Immutability Matters

**1. Predictability**

- No unexpected side effects
  **2. Easier Debugging**
- State doesn’t change unexpectedly
  **3. Performance (in some cases)**
- Enables reference comparison

```c
oldObj === newObj
```

**4. Concurrency Safety**

- No shared mutable state issues

### 🚀 Real-World Use Cases

- React state updates
- Redux store
- Functional programming
- Backend caching systems

### ⚠️ Common Pitfall

**Shallow Copy Issue**

```c
const obj = { a: { b: 1 } };

const newObj = { ...obj };
newObj.a.b = 2;

console.log(obj.a.b); // 2 ❌
```

👉 Nested objects still mutable

### 🔧 Enforcing Immutability

```c
Object.freeze(obj);
```

👉 Prevents modification (shallow)

### 🔥 Interview-Level Answer (Polished)

Immutability is the concept of not modifying existing data but instead creating new copies with updated values. It helps in maintaining predictable state, avoiding side effects, and improving performance through easier change detection. While primitives in JavaScript are immutable, objects and arrays are mutable by default, so immutability is typically achieved using techniques like spread operators or libraries.

### 🧩 Bonus Insight

- Used heavily in:
  - Functional programming
  - State management libraries
- Enables:
  - Time-travel debugging
  - Undo/redo systems

### ⚡ Pro Tip (Interview Gold)

👉 “Immutability = safer state management + fewer bugs”

# 43. What is Object.freeze()?

`Object.freeze()` is a method in JavaScript that makes an object immutable, meaning you **cannot add, delete, or modify its properties**.

### 🧠 Core Idea

👉 “Lock the object so it can’t be changed”

### 🔍 Basic Example

```c
const obj = {
  name: "Alice",
};

Object.freeze(obj);

obj.name = "Bob"; // ❌ ignored (or error in strict mode)

console.log(obj.name); // Alice
```

### ⚙️ What `Object.freeze()` Does

After freezing:

- ❌ Cannot modify properties
- ❌ Cannot add new properties
- ❌ Cannot delete properties
- ❌ Cannot change property descriptors

### 🔬 Under the Hood

It:

- Sets `writable: false`
- Sets `configurable: false`

### ⚠️ Important Limitation (Interview Trap 🚨)

👉 **It is shallow**

```c
const obj = {
  user: { name: "Alice" },
};

Object.freeze(obj);

obj.user.name = "Bob"; // ✅ allowed ❗

console.log(obj.user.name); // Bob
```

👉 Nested objects are still mutable

### 🔧 Deep Freeze (Custom Solution)

```c
function deepFreeze(obj) {
  Object.keys(obj).forEach((key) => {
    if (typeof obj[key] === "object" && obj[key] !== null) {
      deepFreeze(obj[key]);
    }
  });
  return Object.freeze(obj);
}
```

### 🔍 Related Methods

| Method                       | Behavior                       |
| ---------------------------- | ------------------------------ |
| `Object.freeze()`            | No changes allowed             |
| `Object.seal()`              | Can modify, but not add/remove |
| `Object.preventExtensions()` | Can't add new properties       |

### 🎯 Real-World Use Cases

- Prevent accidental mutations
- Protect config objects
- Enforce immutability in state management

### ⚠️ Strict Mode Behavior

```c
"use strict";

const obj = Object.freeze({ a: 1 });
obj.a = 2; // ❌ throws error
```

👉 Without strict mode → silently ignored

### 🔥 Interview-Level Answer (Polished)

`Object.freeze()` is a JavaScript method used to make an object immutable by preventing the addition, deletion, or modification of its properties. However, it performs a shallow freeze, meaning nested objects can still be modified unless explicitly frozen as well.

### 🧩 Bonus Insight

- Common in:
  - Redux (dev mode checks)
  - Defensive programming
- Helps avoid side effects

### ⚡ Pro Tip (Interview Gold)

👉 Always mention:
**“Object.freeze is shallow, not deep”**

# 44. What is `call`, `apply`, `bind`?

`call`, `apply`, and `bind` are methods used to explicitly set the value of `this` when calling a function.

### 🧠 Core Idea

👉 “Control what this points to”

### 🔍 Example Setup

```c
function greet() {
  console.log("Hello " + this.name);
}

const user = { name: "Alice" };
```

### ⚙️ 1. `call()`

👉 Invokes function immediately
👉 Arguments passed individually

```c
greet.call(user); // Hello Alice
```

With arguments:

```c
function greet(age) {
  console.log(this.name, age);
}

greet.call(user, 25);
```

### ⚙️ 2. `apply()`

👉 Same as `call`, but arguments passed as array

```c
greet.apply(user, [25]);
```

### ⚙️ 3. `bind()`

👉 Does NOT call immediately
👉 Returns a new function

```c
const boundFn = greet.bind(user);

boundFn(); // Hello Alice
```

### 🔥 Key Differences

| Feature              | call            | apply | bind            |
| -------------------- | --------------- | ----- | --------------- |
| Executes immediately | ✅              | ✅    | ❌              |
| Arguments            | comma-separated | array | comma-separated |
| Returns function     | ❌              | ❌    | ✅              |

### 🔄 Real-World Example

```c
const user = {
  name: "Alice",
};

function greet(city) {
  console.log(this.name, city);
}

const bound = greet.bind(user, "Delhi");

bound(); // Alice Delhi
```

### ⚠️ Common Pitfalls

**Losing** `this`

```c
const obj = {
  name: "JS",
  show() {
    setTimeout(function () {
      console.log(this.name);
    }, 1000);
  },
};
```

👉 Fix:

```c
setTimeout(function () {
  console.log(this.name);
}.bind(this), 1000);
```

### 🎯 When to Use What

- `call` → quick one-time invocation
- `apply` → when arguments are in array
- `bind` → when you need a reusable function

### 🔥 Interview-Level Answer (Polished)

`call`, `apply`, and `bind` are JavaScript methods used to control the value of `this` in a function. `call` and apply invoke the function immediately, with `call` accepting arguments individually and apply accepting them as an array. bind, on the other hand, returns a new function with `this` permanently bound, which can be invoked later.

### 🧩 Bonus Insight

- Used in:
  - Event handlers
  - Borrowing methods
  - Function reuse

### ⚡ Pro Tip (Interview Gold)

👉 “`bind` is for later execution, `call/apply` are for immediate execution”

# 45. What is module pattern?

The **Module Pattern** is a design pattern used to create **private and public** scope using closures, allowing you to encapsulate data and expose only selected functionality.

### 🧠 Core Idea

👉 “Hide internal details, expose only what’s needed”

### 🔍 Basic Example

```c
const Counter = (function () {
  let count = 0; // private

  return {
    increment() {
      count++;
    },
    get() {
      return count;
    },
  };
})();

Counter.increment();
console.log(Counter.get()); // 1
```

### 💡 What’s happening?

- IIFE runs immediately
- **count** is private
- Returned object exposes public methods
- Closure keeps **count** alive

### 🔐 Private vs Public

```c
const module = (function () {
  let privateVar = "secret";

  function privateMethod() {
    console.log(privateVar);
  }

  return {
    publicMethod() {
      privateMethod();
    },
  };
})();
```

👉 Only `publicMethod` is accessible

### 🎯 Why Use Module Pattern?

**1. Encapsulation**

- Hide implementation details
  **2. Avoid Global Pollution**
- No variables leak to global scope
  **3. Data Privacy**
- Protect internal state

### ⚙️ Variations

**Revealing Module Pattern**

```c
const module = (function () {
  function privateFn() {
    console.log("Hello");
  }

  function publicFn() {
    privateFn();
  }

  return {
    publicFn,
  };
})();
```

👉 Cleaner syntax

### 🚀 Real-World Use Cases

- Utility libraries
- Configuration modules
- State management (before modern frameworks)

### ⚠️ Limitations

- Not dynamic (hard to extend)
- Harder to test private methods
- Largely replaced by ES Modules

### 🔄 Modern Alternative

```c
// ES Module
let count = 0;

export function increment() {
  count++;
}

export function get() {
  return count;
}
```

👉 Native module system (preferred today)

### 🔥 Interview-Level Answer (Polished)

The module pattern is a design pattern in JavaScript that uses closures to create private and public members, allowing encapsulation and data hiding. It typically uses an IIFE to create a private scope and returns an object exposing only the public API. This helps prevent global namespace pollution and improves code organization.

### 🧩 Connection to Concepts

- Uses closures
- Often implemented with IIFE
- Related to encapsulation

### ⚡ Pro Tip (Interview Gold)

👉 “Module pattern = closure + IIFE + encapsulation”

# 46. What is tree shaking?

`Tree shaking` is a process used by bundlers to `remove` unused code (dead code) from the final bundle, reducing bundle size and improving performance.

### 🧠 Core Idea

👉 “Only include what is actually used”

### 🔍 Example

```c
// utils.js
export function add(a, b) {
  return a + b;
}

export function multiply(a, b) {
  return a * b;
}
```

```c
// app.js
import { add } from "./utils.js";

console.log(add(2, 3));
```

### 📦 Final Bundle (after tree shaking)

```c
function add(a, b) {
  return a + b;
}

console.log(add(2, 3));
```

👉 `multiply` is removed ❌

### ⚙️ How It Works

Tree shaking relies on:

- **Static** analysis of imports/exports
- ES Modules (`import/export`)

### 🚀 Tools That Support Tree Shaking

- Webpack
- Rollup
- Vite
- esbuild

### ⚠️ Important Requirements

**1. Must use ES Modules**

```c
import { x } from "module"; // ✅
require("module");          // ❌ (CommonJS not tree-shakable)
```

**2. Must be statically analyzable**

```c
// ❌ dynamic import
const fn = module[methodName];
```

**3. Side effects matter**

```c
import "./file.js"; // may not be removed
```

👉 Because it might have side effects

### ⚠️ Common Pitfall

```c
export const data = fetchData();
```

👉 Might not be removed due to side effects

### 🎯 Real-World Benefits

- Smaller bundle size
- Faster load time
- Better performance

### 🔥 Tree Shaking vs Dead Code Elimination

| Feature | Tree Shaking | Dead Code Elimination |
| ------- | ------------ | --------------------- |
| Level   | Module level | Code level            |
| Tool    | Bundler      | Minifier              |

### 🔥 Interview-Level Answer (Polished)

Tree shaking is an optimization technique used by modern JavaScript bundlers to eliminate unused code from the final bundle. It works by statically analyzing ES module imports and exports and removing parts of the code that are not used. This results in smaller bundle sizes and improved application performance.

### 🧩 Bonus Insight

- Works best with:
  - Pure functions
  - Side-effect-free modules
- Often combined with:
  - Minification
  - Code splitting

### ⚡ Pro Tip (Interview Gold)

👉 “Tree shaking only works with ES Modules because they are statically analyzable.”

# 47. What is shadow DOM?

**Shadow DOM** is a browser feature that allows you to **encapsulate** a part of the **DOM**, isolating its structure, styles, and behavior from the rest of the document.

### 🧠 Core Idea

👉 “Create a private **DOM tree** inside an element”

### 🔍 Why Shadow DOM?

Normally:

- CSS leaks globally ❌
- JS can access everything ❌

With Shadow DOM:

- Styles are scoped ✅
- DOM is isolated ✅

### 🌳 Example

```c
const host = document.getElementById("app");

// attach shadow root
const shadow = host.attachShadow({ mode: "open" });

shadow.innerHTML = `
  <style>
    p { color: red; }
  </style>
  <p>Hello Shadow DOM</p>
`;
```

### 💡 What’s happening?

- `host` → normal DOM element
- `shadow` → separate DOM tree
- Styles inside shadow don’t affect outside

### 🔒 Encapsulation

```c
<p>Hello</p>
```

```c
p { color: blue; }
```

👉 This CSS will NOT affect shadow DOM content

### ⚙️ Modes

**1. Open Mode**

```c
element.attachShadow({ mode: "open" });
```

👉 Accessible via:

```c
element.shadowRoot
```

**2. Closed Mode**

```c
element.attachShadow({ mode: "closed" });
```

👉 Not accessible from outside

### 🧱 Shadow DOM Structure

```
Host Element
   ↓
Shadow Root
   ↓
Shadow DOM Tree
```

### 🎯 Real-World Use Cases

- Web Components
- UI libraries
- Reusable widgets (buttons, modals)

👉 Used internally by:

- `<video>`, `<input>`, `<select>` elements

### ⚠️ Key Features

- Style encapsulation
- DOM isolation
- Slot-based content projection

### 🔄 Slots (Important)

```c
<my-component>
  <span slot="title">Hello</span>
</my-component>
```

👉 Allows passing content into shadow DOM

### 🔥 Shadow DOM vs Regular DOM

| Feature | Regular DOM | Shadow DOM   |
| ------- | ----------- | ------------ |
| Scope   | Global      | Encapsulated |
| CSS     | Global      | Scoped       |
| Access  | Full        | Limited      |

### 🔥 Interview-Level Answer (Polished)

Shadow DOM is a web platform feature that allows developers to create a scoped and encapsulated DOM subtree attached to an element. It isolates styles and markup from the main document, preventing conflicts and enabling reusable, self-contained components. It is a core part of Web Components.

### 🧩 Bonus Insight

- Part of:
  - Web Components API
- Works with:
  - Custom Elements
  - HTML Templates

### ⚡ Pro Tip (Interview Gold)

👉 “Shadow DOM = encapsulation for the DOM and CSS”

# 48. What is memory leak?

A **memory leak** occurs when memory that is no longer needed is not released, causing the application’s memory usage to grow over time.

### 🧠 Core Idea

👉 “Unused memory stays allocated instead of being garbage collected”

### 🔍 Why It Happens?

JavaScript uses automatic garbage collection, but:

👉 If objects are still **reachable**, they are not cleaned up

### ⚠️ Example

```c
let data = [];

function add() {
  data.push(new Array(1000000).fill("🔥"));
}
```

👉 Every call:

- Adds large data
- Never removed ❌
- Memory keeps increasing → leak

### 🚨 Common Causes of Memory Leaks

**1. Global Variables**

```c
globalVar = "I am global"; // ❌
```

👉 Never garbage collected

**2. Closures Holding References**

```c
function outer() {
  let bigData = new Array(1000000).fill("data");

  return function () {
    console.log("Using data");
  };
}

const fn = outer();
```

👉 `bigData` stays in memory because closure references it

**3. Unremoved Event Listeners**

```c
element.addEventListener("click", handler);
```

👉 If not removed:

- Keeps reference alive
  **4. Timers Not Cleared**

```c
setInterval(() => {
  console.log("running");
}, 1000);
```

👉 Keeps running → memory retained

**5. Caches Growing Indefinitely**

```c
const cache = {};

cache[key] = largeData;
```

👉 Without eviction → leak

### 🔄 How Garbage Collection Relates

👉 GC removes only:

- **Unreachable objects**

👉 Memory leak happens when:

- Objects are still **reachable unintentionally**

### 📉 Real-World Impact

- Increased memory usage
- Slower performance
- App crashes (Out of Memory)
- Node.js server restarts

### 🔧 How to Prevent

- Avoid global variables
- Remove event listeners
- Clear timers (`clearInterval`)
- Limit cache size (LRU, TTL)
- Nullify unused references

```c
obj = null;
```

### 🛠️ Debugging Tools

- Chrome DevTools → Heap snapshot
- Node.js → `--inspect`
- Memory profiling tools

### 🔥 Interview-Level Answer (Polished)

A memory leak occurs when memory that is no longer needed is not released because it is still referenced, preventing the garbage collector from reclaiming it. Over time, this leads to increased memory usage and potential application crashes. Common causes include global variables, unremoved event listeners, closures holding references, and unbounded caches.

### 🧩 Bonus Insight

- Memory leaks are critical in long-running systems like:
  - Node.js servers
- Often caused by bad reference management

### ⚡ Pro Tip (Interview Gold)

👉 “Garbage collector removes only unreachable objects—memory leaks happen when objects remain reachable unintentionally.”

# 49. What is WeakMap?

A WeakMap is a collection of **key-value pairs where keys must be objects**, and the keys are held weakly, meaning they can be garbage collected if no other references exist.

### 🧠 Core Idea

👉 “Store data tied to objects without preventing their garbage collection”

### 🔍 Basic Example

```c
const wm = new WeakMap();

let obj = { name: "Alice" };

wm.set(obj, "some metadata");

console.log(wm.get(obj)); // "some metadata"

obj = null; // remove reference
```

👉 Now:

- Object becomes unreachable
- Garbage collector can clean it
- Entry in WeakMap is removed automatically ✅

### ⚠️ Key Characteristics

**1. Keys must be objects**

```c
wm.set(1, "value"); // ❌ Error
```

**2. Weak references**

- Does NOT prevent garbage collection
- Helps avoid memory leaks
  **3. Not iterable ❗**

```c
wm.keys(); // ❌ not allowed
```

👉 Reason:

- Keys may disappear anytime due to GC
  **4. No size property**

```c
wm.size // ❌ undefined
```

### 🔄 WeakMap vs Map

| Feature     | Map              | WeakMap                     |
| ----------- | ---------------- | --------------------------- |
| Key type    | Any              | Only objects                |
| GC behavior | Strong reference | Weak reference              |
| Iterable    | ✅               | ❌                          |
| Use case    | General storage  | Memory-safe object metadata |

### 🎯 Real-World Use Cases

**1. Private Data Storage**

```c
const privateData = new WeakMap();

class User {
  constructor(name) {
    privateData.set(this, { name });
  }

  getName() {
    return privateData.get(this).name;
  }
}
```

👉 Data is:

- Hidden
- Garbage collected when object is gone
  **2. Avoid Memory Leaks**
- Storing metadata for DOM elements
- Caching without retaining objects

### ⚠️ Why Not Use Map?

```c
const map = new Map();

let obj = {};
map.set(obj, "data");

obj = null;
```

👉 Object still referenced by Map ❌ → memory leak risk

### 🔥 Interview-Level Answer (Polished)

A WeakMap is a key-value collection where keys must be objects and are held weakly, meaning they do not prevent garbage collection. When an object key becomes unreachable, its corresponding entry is automatically removed. WeakMaps are useful for storing metadata or private data without causing memory leaks.

### 🧩 Bonus Insight

- Related concept: Garbage Collection
- Similar structure: `WeakSet`
- Used internally in frameworks for memory-safe references

### ⚡ Pro Tip (Interview Gold)

👉 “WeakMap prevents memory leaks by not holding strong references to keys”

# 50. Explain JS single-threaded nature

JavaScript is `single-threaded`, meaning it executes code `one task at a time on a single call stack`.

### 🧠 Core Idea

👉 “Only one thing runs at a time”

### 🔍 What does Single-Threaded Mean?

- JS has **one call stack**
- Executes code **line by line**
- Cannot run multiple pieces of JS code simultaneously (by default)

### 📦 Example

```c
console.log("A");

console.log("B");

console.log("C");
```

👉 Output:

```
A
B
C
```

👉 Executes sequentially

### ⚠️ Problem with Single Thread

👉 Blocking operations can freeze the app

```c
while (true) {}
```

❌ Blocks everything:

- UI freezes
- No other code runs

### 🚀 So How Does JS Handle Async Work?

👉 Using:

- **Event Loop**
- **Web APIs / Node APIs**
- **Task Queues (Microtask & Macrotask)**

### 🔄 Example (Async Behavior)

```c
console.log("Start");

setTimeout(() => {
  console.log("Async");
}, 0);

console.log("End");
```

👉 Output:

```
Start
End
Async
```

### 💡 Why?

- JS runs sync code first
- Async task goes to callback queue
- Event loop pushes it later

### 🧠 Important Clarification

👉 JavaScript is:

- **Single-threaded execution model **
- But supports concurrency via event loop

### 🔧 Behind the Scenes

Even though JS is single-threaded:

- Browser provides:
  - Web APIs (timers, DOM, fetch)
- Node.js provides:
  - libuv (thread pool, async I/O)

### 🎯 Real-World Implication

- Good for:
  - Simplicity
  - Predictable execution
- Needs:
  - Async programming (Promises, async/await)

### 🔥 Interview-Level Answer (Polished)

JavaScript is single-threaded, meaning it executes code on a single call stack, one operation at a time. However, it handles asynchronous operations efficiently using the event loop, which allows non-blocking behavior by delegating tasks like I/O and timers to external APIs and processing their callbacks later through task queues.

### 🧩 Bonus Insight

- Single-threaded ≠ slow
- It uses:
  - Concurrency (event loop)
  - Not true parallelism

### ⚡ Pro Tip (Interview Gold)

👉 “JavaScript is single-threaded, but not blocking—thanks to the event loop.”
