# 31. What is an Execution Plan?

An Execution Plan (or Query Execution Plan) is how a database decides to execute a SQL query step-by-step.

### 🔹 Definition

An Execution Plan is a blueprint that shows how the database will retrieve data to run your query.

### 🧠 Key Idea

SQL tells what you want → Execution plan decides how to get it

### 🔹 Why It Matters

Two queries can look the same but perform very differently depending on the execution plan.

👉 It helps you:

- Debug slow queries 🐢
- Understand performance bottlenecks
- Optimize indexes & joins

### 🔹 Example Query

```
SELECT * FROM users WHERE email = 'test@example.com';
```

### 🔹 Possible Execution Plans

❌ **Without Index**

```
Full Table Scan → check every row
```

✅ **With Index**

```
Index Seek → directly jump to matching row
```

👉 Huge performance difference 🚀

### 🔹 What Does an Execution Plan Show?

- Table scans vs index scans
- Join methods
- Order of operations
- Estimated cost
- Rows processed

### 🔹 Common Operations

**1. Table Scan**

- Reads entire table
  ❌ Slow for large data
  **2. Index Seek**
- Uses index to find rows
  ✅ Fast
  **3. Index Scan**
- Scans index (not full table)
  **4. Nested Loop Join**
- Loop one table inside another
  ✅ Good for small datasets
  **5. Hash Join**
- Uses hashing for matching
  ✅ Good for large datasets
  **6. Sort / Aggregate**
  Sorting or grouping data

### 🔹 How to View Execution Plan

**In MySQL:**

```
EXPLAIN SELECT * FROM users;
```

**In PostgreSQL:**

```
EXPLAIN ANALYZE SELECT * FROM users;
```

### 🔹 Example Output (Simplified)

```
Seq Scan on users  (cost=0.00..100.00 rows=1000)
```

👉 Means:

- Sequential scan (full table)
- Estimated cost = 100

### 🔹 Estimated vs Actual Plan

| Type           | Meaning                    |
| -------------- | -------------------------- |
| Estimated Plan | What DB thinks will happen |
| Actual Plan    | What actually happened     |

### 🔹 Why Execution Plans Change?

- Missing indexes
- Data size changes
- Query structure
- Statistics updates

### 🔹 Advantages

✅ Helps optimize queries
✅ Identifies slow operations
✅ Guides indexing strategy

### 🔹 Disadvantages

❌ Can be complex to read
❌ DB-specific format
❌ Requires experience to interpret

### 🧠 Real-World Example

🛒 **E-commerce:**

Slow query:

```
SELECT * FROM orders WHERE user_id = 100;
```

Execution plan shows:

```
Full Table Scan
```

👉 Fix:

```
CREATE INDEX idx_user_id ON orders(user_id);
```

### 🧠 Simple Analogy

- **SQL Query** → “Find a book in a library”
- **Execution Plan** → “Do I scan all shelves or use the catalog?”

### 🔥 Interview Insight

👉 Most performance issues = bad execution plans
👉 Always check:

- Index usage
- Join type
- Scan type

# 32. What is an Aggregate Function?

An Aggregate Function in SQL is a function that performs a calculation on multiple rows and returns a single value.

### 🔹 Definition

An Aggregate Function processes a group of rows and returns one result.

### 🧠 Key Idea

```
Many rows → One result
```

### 🔹 Common Aggregate Functions

**1. COUNT()**

Counts number of rows

```
SELECT COUNT(*) FROM users;
```

👉 Counts all rows

```
SELECT COUNT(email) FROM users;
```

👉 Counts non-null values only

**2. SUM()**

Adds values

```
SELECT SUM(amount) FROM orders;
```

**3. AVG()**

Calculates average

```
SELECT AVG(price) FROM products;
```

**4. MIN()**

Finds smallest value

```
SELECT MIN(age) FROM users;
```

**5. MAX()**

Finds largest value

```
SELECT MAX(salary) FROM employees;
```

### 🔹 Using with GROUP BY (Very Important 🔥)

Aggregate functions are often used with GROUP BY.

👉 **Example:**

```c
SELECT user_id, COUNT(*) AS total_orders
FROM orders
GROUP BY user_id;
```

👉 Result:

- One row per user
- Count of orders per user

### 🔹 Using with HAVING

Filter aggregated results:

```c
SELECT user_id, COUNT(*) AS total_orders
FROM orders
GROUP BY user_id
HAVING COUNT(*) > 5;
```

👉 Only users with more than 5 orders

### 🔹 Important Behavior

**NULL Handling**

- Most aggregate functions ignore NULL values
- `COUNT(*)` includes all rows
- `COUNT(column)` excludes NULLs

### 🔹 Aggregate vs Normal Function

| Feature | Aggregate Function | Normal Function   |
| ------- | ------------------ | ----------------- |
| Input   | Multiple rows      | Single row        |
| Output  | Single value       | Single value      |
| Example | COUNT(), SUM()     | UPPER(), LENGTH() |

### 🔹 Real-World Examples

🛒 **E-commerce**

```
SELECT SUM(amount) FROM orders;
```

👉 Total revenue

📊 **Analytics**

```
SELECT AVG(session_time) FROM user_sessions;
```

👉 Average session duration

👥 **User Insights**

```
SELECT COUNT(*) FROM users;
```

👉 Total users

### 🔹 Advantages

✅ Simplifies data analysis
✅ Works well with grouping
✅ Essential for reporting

### 🔹 Disadvantages

❌ Limited to predefined operations
❌ Can be slow on huge datasets without indexing

### 🧠 Simple Analogy

- Aggregate Function → Summary of data
- Like:
  - Total marks
  - Average score
  - Highest marks

### 🔥 Interview Insight

👉 Most SQL analytics questions = **GROUP BY** + Aggregate Functions
👉 Very commonly used with:

- JOIN
- HAVING
- ORDER BY

# 33. Difference Between WHERE and HAVING

The difference between WHERE and HAVING is one of the most important SQL concepts, especially when working with aggregation.

### 🔹 Core Difference

| Feature                     | WHERE           | HAVING         |
| --------------------------- | --------------- | -------------- |
| Filters                     | Rows            | Groups         |
| Used with                   | Normal queries  | `GROUP BY`     |
| Execution order             | Before grouping | After grouping |
| Can use aggregate functions | ❌ No           | ✅ Yes         |

### 🧠 Key Idea

**WHERE filters individual rows**
**HAVING filters grouped results**

### 🔹 Example Without GROUP BY (WHERE)

```
SELECT *
FROM users
WHERE age > 25;
```

👉 Filters rows before any grouping

### 🔹 Example With GROUP BY + HAVING

```
SELECT user_id, COUNT(*) AS total_orders
FROM orders
GROUP BY user_id
HAVING COUNT(*) > 5;
```

👉 Filters groups (users with more than 5 orders)

### 🔥 Important Rule

❌ This will NOT work:

```
SELECT user_id, COUNT(*)
FROM orders
WHERE COUNT(*) > 5
GROUP BY user_id;
```

👉 Because WHERE runs before aggregation

### 🔹 Using WHERE + HAVING Together

```
SELECT user_id, COUNT(*) AS total_orders
FROM orders
WHERE status = 'completed'
GROUP BY user_id
HAVING COUNT(*) > 5;
```

👉 Execution Flow:

- **WHERE** → filter rows (status = completed)
- **GROUP BY** → group by user
- **HAVING** → filter groups

### 🔹 Execution Order (Very Important 🔥)

```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
```

### 🔹 Real-World Example

🛒 **E-commerce:**

Find users who:

- Have completed orders
- And placed more than 3 orders

```c
SELECT user_id, COUNT(*) AS total_orders
FROM orders
WHERE status = 'completed'
GROUP BY user_id
HAVING COUNT(*) > 3;
```

### 🧠 Simple Analogy

- **WHERE** → Filter students before grouping
- **HAVING** → Filter groups after calculating average

👉 Example:

- WHERE → students with marks > 50
- HAVING → classes with average > 70

### 🔥 Interview Tips

👉 Always remember:

- `WHERE` → before aggregation
- `HAVING` → after aggregation

👉 Use:

- `WHERE` for performance (filters early)
- `HAVING` only when needed

# 34. Index Scan vs Index Seek

The difference between Index Scan and Index Seek is a core concept in understanding query performance and execution plans.

### 🔹 Core Difference

| Feature       | Index Seek               | Index Scan                  |
| ------------- | ------------------------ | --------------------------- |
| Access method | Direct lookup            | Sequential scan             |
| Rows read     | Only required rows       | Many / all rows             |
| Performance   | 🚀 Fast                  | 🐢 Slower                   |
| Use case      | Highly selective queries | Low selectivity / no filter |

### 🧠 Key Idea

**Index Seek** = precise search (like binary search)
**Index Scan** = scanning through index (like reading pages)

### 🔹 Index Seek

👉 **What it does:**

- Uses the index to jump directly to matching rows
- Efficient for exact matches or small ranges
  👉 **Example:**

```
SELECT *
FROM users
WHERE id = 100;
```

👉 **If `id` is indexed:**

```
Index Seek → directly find row 100
```

### 🔹 Index Scan

👉 **What it does:**

- Reads entire index (or large portion) sequentially
- Still better than full table scan, but slower than seek
  👉 **Example:**

```c
SELECT *
FROM users
WHERE age > 18;
```

👉 **If many rows match:**

```
Index Scan → scans large part of index
```

### 🔹 Visual Intuition

```
Index Seek:
[Jump → Exact Location]

Index Scan:
[Start → Read → Read → Read → ...]
```

### 🔹 When Does Index Seek Happen?

✅ Indexed column used
✅ Highly selective condition
✅ Equality or narrow range

```
WHERE id = 10
WHERE email = 'abc@test.com'
```

### 🔹 When Does Index Scan Happen?

❌ Low selectivity (many rows match)
❌ No proper index
❌ Functions on indexed column

```
WHERE age > 18
WHERE YEAR(created_at) = 2024  -- breaks index usage
```

### 🔥 Important Concept: Selectivity

Selectivity = how unique your data is

- High selectivity → Index Seek
- Low selectivity → Index Scan

### 🔹 Real Execution Plan Example

```
Index Seek (cost=5)
Index Scan (cost=120)
```

👉 Lower cost = better plan

### 🔹 How to Force Index Seek (Optimization Tips)

✅ **Use proper indexes**

```
CREATE INDEX idx_email ON users(email);
```

✅ **Avoid functions on indexed columns**

❌ Bad:

```
WHERE LOWER(email) = 'abc@test.com'
```

✅ **Good:**

```
WHERE email = 'abc@test.com'
```

✅ **Use correct data types**

- Mismatch → no index usage

### 🔹 Index Scan vs Table Scan

| Feature    | Index Scan  | Table Scan   |
| ---------- | ----------- | ------------ |
| Uses index | ✅ Yes      | ❌ No        |
| Speed      | Medium      | Slow         |
| Data read  | Index pages | Entire table |

### 🔹 Real-World Example

🛒 **E-commerce:**

```
SELECT * FROM orders WHERE order_id = 101;
```

👉 Index Seek (fast)

```
SELECT * FROM orders WHERE status = 'shipped';
```

👉 Index Scan (many rows)

### 🧠 Simple Analogy

- **Index Seek** → Using book index to jump to page 📖
- **Index Scan** → Flipping through pages

### 🔥 Interview Insight

👉 Not all index usage = fast
👉 Index Scan can still be slow

👉 Goal:

- Prefer Index Seek
- Avoid unnecessary scans

# 35. What is Data Integrity?

Data Integrity in databases means ensuring that data is accurate, consistent, and reliable throughout its lifecycle.

### 🔹 Definition

Data Integrity ensures that data remains correct, valid, and unchanged (unless properly modified).

### 🧠 Key Idea

“Your data should always be trustworthy”

### 🔹 Why Data Integrity Matters

- Prevents incorrect data ❌
- Ensures consistency across tables ✅
- Maintains trust in the system 🔒
- Critical for systems like banking, healthcare, etc.

### 🔹 Types of Data Integrity

**1. Entity Integrity**

Ensures:

- Each row is uniquely identifiable

👉 Achieved using:

- Primary Key

```
id INT PRIMARY KEY
```

**2. Referential Integrity**

Ensures:

- Relationships between tables remain valid

👉 Achieved using:

- Foreign Key

```
FOREIGN KEY (user_id) REFERENCES users(id)
```

👉 Prevents:

- Orders without a valid user ❌
  **3. Domain Integrity**

Ensures:

- Data follows valid rules and formats

👉 Examples:

```
age INT CHECK (age >= 18)
email VARCHAR(255) NOT NULL
```

**4. User-Defined Integrity**

Custom business rules

👉 Example:

```
salary > 0
order_amount <= account_balance
```

### 🔹 How to Maintain Data Integrity

✅ **Constraints**

- PRIMARY KEY
- FOREIGN KEY
- UNIQUE
- NOT NULL
- CHECK
  ✅ **Transactions (ACID Properties)**
- Atomicity → all or nothing
- Consistency → valid state
- Isolation → no interference
- Durability → permanent changes
  ✅ **Triggers**
- Automatically enforce rules
  ✅ **Validations in Application Layer**
- Input checks before DB insert-

### 🔹 Example

🏦 **Banking System**

```
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
```

👉 Must ensure:

- No money lost
- No negative balance

➡️ Done using:

- Transactions + constraints

### 🔹 Data Integrity vs Data Security

| Feature | Data Integrity         | Data Security                       |
| ------- | ---------------------- | ----------------------------------- |
| Focus   | Accuracy & consistency | Protection from unauthorized access |
| Example | Correct balance        | Prevent hacking                     |

### 🔹 Advantages

✅ Reliable data
✅ Prevents corruption
✅ Better decision making
✅ Maintains consistency

### 🔹 Disadvantages (Trade-offs)

❌ Can slow down performance (due to checks)
❌ Requires proper design

### 🧠 Real-World Example

🛒 **E-commerce**

- Order must reference valid user
- Price cannot be negative
- Stock cannot go below zero

### 🧠 Simple Analogy

- Data Integrity → Keeping records in a notebook correct
- No duplicate entries
- No wrong values
- No missing references

### 🔥 Interview Insight

👉 Data Integrity = **Constraints** + **Transactions** + **Good Design**

👉 Most bugs in production systems =
❌ Broken integrity (not security issues)

# 36. What is CAP Theorem?

The CAP Theorem is a fundamental concept in distributed systems that explains the trade-offs between Consistency, Availability, and Partition Tolerance.

### 🔹 Definition

The CAP Theorem states that a distributed system can guarantee only two out of three:

- C → Consistency
- A → Availability
- P → Partition Tolerance

### 🧠 Key Idea

In the presence of a network failure, you must choose between Consistency and Availability

### 🔹 The Three Components

**1. Consistency (C)**

- Every read gets the latest data
- All nodes show the same result

👉 Example:

- Update user name → all users see updated name immediately
  **2. Availability (A)**
- System always responds
- Even if data might be outdated

👉 Example:

- You always get a response, even during failures
  **3. Partition Tolerance (P)**
- System continues to work despite network failures

👉 Example:

- Nodes cannot communicate, but system still runs

### 🔥 The Trade-Off

In real-world systems:

- Network failures (partitions) are unavoidable
  - 👉 So you must choose:
    👉 **CP (Consistency + Partition Tolerance)**
- Accurate data
- May reject requests (less available)
  👉 **AP (Availability + Partition Tolerance)**
- Always responds
- May return stale data
  👉 **CA (Consistency + Availability)**
- Possible only when no network partition
- Not practical in distributed systems

### 🔹 Visual Idea

```
        C
       / \
      /   \
     /     \
    A-------P
```

👉 You can only pick two sides at a time

### 🔹 Real-World Examples

**CP Systems**

- Strong consistency
- May block during failure

Used by:

- HBase
- MongoDB (in some modes)
  **AP Systems**
- High availability
- Eventual consistency

Used by:

- Amazon (DynamoDB design)
- Cassandra
  **CA Systems**
- Traditional single-node DBs
- No partition tolerance

### 🔹 Eventual Consistency (Important 🔥)

AP systems often use:

**Eventual Consistency** → Data becomes consistent over time

👉 Example:

- You post something
- Friend sees it after a few seconds

### 🔹 Why CAP Theorem Matters

- Helps design scalable systems
- Explains trade-offs in distributed DBs
- Guides architecture decisions

### 🔹 CAP vs ACID

| Feature   | CAP                 | ACID                       |
| --------- | ------------------- | -------------------------- |
| Focus     | Distributed systems | Transactions               |
| Trade-off | C vs A              | Consistency vs performance |
| Scope     | System-level        | Database-level             |

### 🧠 Simple Analogy

Imagine:

- Multiple bank branches (servers)

If network breaks:

- Show correct balance (Consistency)?
- Or allow withdrawals anyway (Availability)?

👉 You must choose one

### 🔥 Interview Insight

👉 **P is non-negotiable** in distributed systems
👉 Real choice = **CP vs AP**

# 37. What is Eventual Consistency?

Eventual Consistency is a consistency model in distributed systems where data may not be immediately consistent across all nodes, but will become consistent over time.

### 🔹 Definition

**Eventual Consistency** means that if no new updates occur, all replicas will eventually converge to the same value.

### 🧠 Key Idea

“Data might be temporarily inconsistent, but it will fix itself soon”

### 🔹 Why It Exists

In distributed systems:

- Data is replicated across multiple servers
- Instant synchronization is expensive or slow

👉 So systems prioritize:

- **Availability + Performance** over immediate consistency

### 🔹 Example

👉 **Scenario:**

- - You update your profile name
- - Request goes to Server A (Primary)
- - Replication to Server B, C takes time

👉 Meanwhile:

- Some users see old name
- Others see new name

⏳ After a short time → all servers sync → consistency achieved

### 🔹 Timeline View

```
Time 1 → Update happens
Time 2 → Some nodes updated
Time 3 → All nodes updated ✅
```

### 🔹 Where It’s Used

Systems that need:

- High availability
- Fast response times
- Global distribution
  **Real-world systems:**
- Amazon DynamoDB
- Apache Cassandra
- Facebook feeds

### 🔹 Eventual vs Strong Consistency

| Feature       | Eventual Consistency | Strong Consistency |
| ------------- | -------------------- | ------------------ |
| Data accuracy | Delayed              | Immediate          |
| Availability  | High                 | Lower              |
| Performance   | Fast                 | Slower             |
| Use case      | Social feeds         | Banking systems    |

### 🔹 Advantages

✅ High availability
✅ Low latency (fast responses)
✅ Better scalability
✅ Works well for global apps

### 🔹 Disadvantages

❌ Temporary stale data
❌ Complex conflict resolution
❌ Not suitable for critical systems (e.g., banking)

### 🔹 Real-World Examples

📱 **Social Media**

- You like a post → count updates after a delay
  🛒 **E-commerce**
- Product stock may not update instantly
  📩 **Messaging Apps**
- Messages may appear with slight delay

### 🔹 How Systems Handle It

- Replication mechanisms
- Conflict resolution strategies (last write wins, vector clocks)
- Read repair / background sync

### 🔹 Related to CAP Theorem

👉 Eventual consistency is common in AP systems:

- Prioritize Availability + Partition Tolerance
- Accept temporary inconsistency

### 🧠 Simple Analogy

Group of friends updating a shared note:

- One updates first
- Others see old version briefly
- Eventually everyone sees the same version

### 🔥 Interview Insight

👉 Eventual consistency is a design choice, not a flaw

👉 Used when:

- Speed > Immediate accuracy

The difference between SQL vs NoSQL databases is one of the most fundamental concepts in system design.

### 🔹 Core Difference

| Feature     | SQL                     | NoSQL                        |
| ----------- | ----------------------- | ---------------------------- |

| Scaling     | Vertical                | Horizontal                   |
| Data format | Tables (rows & columns) | JSON, key-value, graph, etc. |
| Consistency | Strong (ACID)           | Often eventual (BASE)        |

### 🧠 Key Idea

- SQL = structured, strict, consistent
- NoSQL = flexible, scalable, fast

### 🔹 SQL Databases

👉 **What they are:**

Relational databases with tables, rows, and relationships

👉 **Examples:**

- MySQL
- PostgreSQL
- Oracle Database
  👉 **Features:**
- Fixed schema
- Supports joins
- ACID transactions
- Strong consistency
  👉 **Example Structure:**
  Users Table
  +----+--------+--------+
  | id | name | email |
  +----+--------+--------+

### 🔹 NoSQL Databases

👉 **What they are:**

Non-relational databases designed for flexibility and scale

👉 **Examples:**

- MongoDB (document)
- Redis (key-value)
- Cassandra (wide-column)
  👉 **Features:**
- Schema-less
- Horizontal scaling
- High performance
- Eventual consistency
  👉 **Example (JSON Document):**

```c
{
  "id": 1,
  "name": "John",
  "email": "john@test.com"

```

### 🔹 Types of NoSQL Databases

| Type      | Example   | Use Case      |

**1. Schema**

- SQL → predefined schema

- SQL → vertical (increase CPU/RAM)

- SQL → strong consistency

  **4. Query Capability**
- SQL → powerful joins & complex queries
- NoSQL → limited joins, optimized for speed

### 🔹 When to Use SQL

✅ Complex queries & joins
✅ Strong consistency needed
✅ Structured data
✅ Transactions (banking, finance)

### 🔹 When to Use NoSQL

✅ Large-scale systems

Modern systems often use both:

👉 Most large systems:

- Start with SQL
- Add NoSQL when scaling

# 39. What is BASE?

BASE is a concept from distributed systems that describes a different way of designing databases compared to traditional ACID systems.

It stands for:

- B → Basically Available
- A → Soft State
- S → Eventual Consistency

### 🔹 1. Basically Available

The system always responds, even if the response is not perfectly up-to-date.

👉 **Example:**
In systems like Amazon DynamoDB, you might get slightly stale data, but the system won’t fail or block.

✔ Focus: High availability over strict correctness

### 🔹 2. Soft State

The system’s state can change over time, even without new input.

👉 **Why?**
Because data is replicated across multiple nodes and updates propagate gradually.

✔ Data is not immediately consistent across all servers.

### 🔹 3. Eventual Consistency

Given enough time (and no new updates), all nodes will eventually have the same data.

👉 **Example:**
If you update a profile:

- Server A updates immediately
- Server B updates after a delay

Eventually → both match.

✔ **Focus:** Consistency is delayed, not ignored

### 🔥 BASE vs ACID (Quick Contrast)

| Feature      | BASE                      | ACID                         |
| ------------ | ------------------------- | ---------------------------- |
| Consistency  | Eventual                  | Strong                       |
| Availability | High                      | Lower (may block)            |
| Use Case     | Distributed / large-scale | Financial / critical systems |
| Example      | Apache Cassandra, MongoDB | Traditional SQL databases    |

### ⚖️ Why BASE Exists (CAP Theorem Connection)

In distributed systems, due to the CAP Theorem:

You can’t have all three:

- Consistency
- Availability
- Partition Tolerance

👉 **BASE systems choose:**

- ✅ Availability
- ✅ Partition Tolerance
- ❌ Immediate Consistency

### 🚀 When to Use BASE

**BASE is ideal when:**

- You’re building highly scalable systems
- Some inconsistency is acceptable
- Examples:
  - Social media feeds
  - Product catalogs
  - Analytics dashboards

### 🧠 Simple Analogy

Think of WhatsApp messages:

- You send a message ✔
- Your friend sees it after a delay ✔
- Eventually, both devices sync ✔

👉 That’s **Eventual Consistency → BASE**

# 40. What is Optimistic Locking?

Optimistic Locking is a concurrency control technique used to prevent conflicts when multiple users try to update the same data without locking it upfront.

Instead of blocking access, it assumes conflicts are rare and checks for them only at the time of update.

### 🔹 Core Idea

“Go ahead and read/update… but before saving, verify nothing has changed.”

### 🔧 How It Works

Usually implemented using a version number or timestamp.

**Step-by-step:**

- Read data (with version)
- Modify data
- Before update → check:
  - Has version changed?
- If YES → ❌ reject (conflict)
- If NO → ✅ update + increment version

### 📦 Example

Imagine a user profile:

```
{
  "name": "John",
  "version": 1
}
```

**Two users:**

- User A reads version = 1
- User B reads version = 1
  **User A updates:**
- version becomes 2 ✅
  **User B tries update:**
- still has version = 1 ❌ conflict detected

👉 User B must retry with fresh data.

### 🔁 Typical SQL Example

```c
UPDATE users
SET name = 'John Updated', version = version + 1
WHERE id = 1 AND version = 1;
```

👉 If no rows updated → conflict occurred.

### 🔥 Why It’s “Optimistic”

Because it does NOT lock resources like traditional systems.

- No blocking
- High performance
- Works well in distributed systems

### ⚖️ Optimistic vs Pessimistic Locking

| Feature           | Optimistic Locking   | Pessimistic Locking      |
| ----------------- | -------------------- | ------------------------ |
| Locking           | No upfront lock      | Locks data before access |
| Performance       | High                 | Lower                    |
| Conflict handling | At write time        | Prevented upfront        |
| Use case          | Low conflict systems | High contention systems  |

### 🧠 Where It’s Used

- ORMs like Hibernate (@Version)
- NoSQL systems like MongoDB (using version fields)
- REST APIs (ETags / If-Match headers)
- Microservices & distributed systems

### 🚀 When to Use Optimistic Locking

Use it when:

- Conflicts are rare
- System is read-heavy
- You want high scalability

Avoid when:

- Frequent concurrent writes
- Critical systems where retries are costly

### 🧩 Real-World Analogy

Think of Google Docs:

- Multiple people edit simultaneously
- System doesn’t lock the document
- Conflicts are resolved when syncing

👉 That’s optimistic locking in spirit.
