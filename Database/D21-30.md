# 21. Types of Joins

SQL joins are used to combine rows from two or more tables based on a related column. Think of joins as ways to “merge” datasets depending on how their data matches.

Let’s go through the main types of joins 👇

### 🔹 1. INNER JOIN

Returns only the rows that have matching values in both tables.

👉 **Example:**

```
SELECT *
FROM users u
INNER JOIN orders o
ON u.id = o.user_id;
```

🧠 **Think:**

Only common data between both tables

### 🔹 2. LEFT JOIN (LEFT OUTER JOIN)

Returns:

- All rows from the left table
- Matching rows from the right table
- If no match → NULL values
  👉 **Example:**

```
SELECT *
FROM users u
LEFT JOIN orders o
ON u.id = o.user_id;
```

🧠 **Think:**

“Give me everything from left, even if right is missing”

### 🔹 3. RIGHT JOIN (RIGHT OUTER JOIN)

Returns:

- All rows from the right table
- Matching rows from the left
- If no match → NULL
  👉 **Example:**

```
SELECT *
FROM users u
RIGHT JOIN orders o
ON u.id = o.user_id;
```

🧠 **Think:**

“Give me everything from right, even if left is missing”

### 🔹 4. FULL JOIN (FULL OUTER JOIN)

Returns:

- All rows from both tables
- Matching where possible
- Non-matching → NULLs
  👉 **Example:**

```
SELECT *
FROM users u
FULL JOIN orders o
ON u.id = o.user_id;
```

🧠 **Think:**

“Give me everything from both sides”

### 🔹 5. CROSS JOIN

Returns Cartesian product:

Every row from table A × every row from table B
👉 **Example:**

```
SELECT *
FROM users
CROSS JOIN products;
```

🧠 **Think:**

All possible combinations (can explode in size ⚠️)

### 🔹 6. SELF JOIN

A table joins with itself.

👉 **Example:**

```
SELECT e1.name, e2.name AS manager
FROM employees e1
JOIN employees e2
ON e1.manager_id = e2.id;
```

🧠 **Think:**

“Compare rows within the same table”

### 🔹 7. NATURAL JOIN (Less Common ⚠️)

Automatically joins columns with the same name.

👉 **Example:**

```c
SELECT *
FROM users
NATURAL JOIN orders;
```

⚠️ **Warning:**

- Can be risky because it auto-matches columns
- Not recommended in production

### 🧾 Quick Comparison Table

| Join Type  | Result              |
| ---------- | ------------------- |
| INNER JOIN | Only matching rows  |
| LEFT JOIN  | All left + matches  |
| RIGHT JOIN | All right + matches |
| FULL JOIN  | All from both       |
| CROSS JOIN | All combinations    |
| SELF JOIN  | Table with itself   |

### 🧠 Visual Intuition (Very Important)

Imagine 2 circles (Venn diagram):

- **INNER JOIN** → intersection
- **LEFT JOIN** → left circle
- **RIGHT JOIN** → right circle
- **FULL JOIN** → both circles

# 22. What is a View?

A View in SQL is a virtual table created from a query. It does not store data itself (in most cases), but shows data from one or more tables dynamically.

### 🔹 Definition

A View is a saved SQL query that you can treat like a table.

### 🔹 Syntax

```
CREATE VIEW view_name AS
SELECT column1, column2
FROM table_name
WHERE condition;
```

### 🔹 Example

```
CREATE VIEW active_users AS
SELECT id, name, email
FROM users
WHERE status = 'active';
```

👉 **Now you can use it like:**

```
SELECT * FROM active_users;
```

### 🧠 Key Idea

A view is just a shortcut for a query, not actual stored data.

### 🔹 Types of Views

**1. Simple View**

- Based on a single table
- No complex operations

```
CREATE VIEW user_names AS
SELECT name FROM users;
```

**2. Complex View**

- Uses joins, aggregations, group by

```
CREATE VIEW user_orders AS
SELECT u.name, COUNT(o.id) AS total_orders
FROM users u
JOIN orders o ON u.id = o.user_id
GROUP BY u.name;
```

### 🔹 Advantages

✅ **Simplifies complex queries**
→ You don’t need to write joins again and again

✅ **Security**
→ Show only specific columns (hide sensitive data like passwords)

✅ **Reusability**
→ Write once, use many times

✅ **Abstraction layer**
→ Changes in base tables can be hidden

### 🔹 Disadvantages

❌ Performance overhead (for complex views)
❌ Limited updates (some views are not updatable)
❌ Depends on underlying tables

### 🔹 Updatable vs Non-Updatable Views

✔ **Updatable View:**

```
CREATE VIEW user_basic AS
SELECT id, name FROM users;
```

You can:

```
UPDATE user_basic SET name = 'John' WHERE id = 1;
```

❌ **Non-Updatable View:**

```
CREATE VIEW user_summary AS
SELECT name, COUNT(*) FROM users GROUP BY name;
```

Cannot update because of `GROUP BY`

### 🔹 Materialized View (Important 🔥)

A Materialized View:

- Stores actual data (unlike normal views)
- Needs manual/periodic refresh

```
CREATE MATERIALIZED VIEW sales_summary AS
SELECT product_id, SUM(amount)
FROM sales
GROUP BY product_id;
```

### 🧠 View vs Table

| Feature        | View             | Table   |
| -------------- | ---------------- | ------- |
| Stores data    | ❌ No            | ✅ Yes  |
| Based on query | ✅ Yes           | ❌ No   |
| Performance    | Slower (dynamic) | Faster  |
| Use case       | Abstraction      | Storage |

### 🧠 Real-World Example

In an **e-commerce app:**

- You have a `users` table with password, email, etc.
- You create a view:

```
CREATE VIEW public_users AS
SELECT id, name FROM users;
```

👉 Frontend queries this view
👉 Sensitive data stays hidden

# 23. What is a Stored Procedure?

A Stored Procedure in SQL is a precompiled, reusable block of SQL code stored in the database that you can execute whenever needed.

### 🔹 Definition

A Stored Procedure is a saved set of SQL statements that performs a specific task and can accept inputs (parameters).

### 🔹 Why use Stored Procedures?

Instead of writing the same SQL logic again and again, you:

- Store it once in the database
- Call it whenever needed

### 🔹 Basic Syntax

```
CREATE PROCEDURE procedure_name
AS
BEGIN
    -- SQL statements
END;
```

### 🔹 Example

```
CREATE PROCEDURE GetAllUsers
AS
BEGIN
    SELECT * FROM users;
END;
```

👉 **Execute it:**

```
EXEC GetAllUsers;
```

### 🔹 Stored Procedure with Parameters

```
CREATE PROCEDURE GetUserById
    @userId INT
AS
BEGIN
    SELECT * FROM users WHERE id = @userId;
END;
```

👉 **Call:**

```
EXEC GetUserById 1;
```

### 🔹 Types of Parameters

**1. Input Parameter**

```
@id INT
```

**2. Output Parameter**

```
CREATE PROCEDURE GetUserCount
    @count INT OUTPUT
AS
BEGIN
    SELECT @count = COUNT(*) FROM users;
END;
```

### 🔹 Key Features

✅ **Reusable logic**
→ Write once, use many times

✅ **Better performance**
→ Precompiled & optimized

✅ **Security**
→ Can restrict direct table access

✅ **Encapsulation**
→ Business logic stays inside DB

### 🔹 Advantages

- Reduces network traffic (send call instead of full query)
- Improves maintainability
- Centralized logic
- Faster execution (in many DBs)

### 🔹 Disadvantages

❌ Harder to debug
❌ DB-dependent (not portable across databases)
❌ Can become complex if overused

### 🔹 Stored Procedure vs Function

| Feature         | Stored Procedure | Function        |
| --------------- | ---------------- | --------------- |
| Returns value   | Optional         | Must return     |
| Can modify data | ✅ Yes           | ⚠️ Limited      |
| Used in SELECT  | ❌ No            | ✅ Yes          |
| Complexity      | High             | Usually simpler |

### 🧠 Real-World Example

In a banking system:

```
CREATE PROCEDURE TransferMoney
    @from INT,
    @to INT,
    @amount DECIMAL
AS
BEGIN
    UPDATE accounts SET balance = balance - @amount WHERE id = @from;
    UPDATE accounts SET balance = balance + @amount WHERE id = @to;
END;
```

👉 Ensures consistent logic for money transfer
👉 Can be combined with transactions for safety

### 🧠 Simple Analogy

- **Query** → One-time instruction
- **View** → Saved SELECT query
- **Stored Procedure** → Full program (with logic + parameters)

# 24. What is a Trigger?

A Trigger in SQL is a special kind of stored program that automatically executes (fires) when a specific event happens in a table.

### 🔹 Definition

A Trigger is a database object that runs automatically in response to events like INSERT, UPDATE, or DELETE.

### 🔹 Key Idea

Unlike a Stored Procedure (which you call manually), a Trigger runs automatically when something changes in the database.

### 🔹 Syntax (General)

```
CREATE TRIGGER trigger_name
ON table_name
AFTER INSERT | UPDATE | DELETE
AS
BEGIN
    -- SQL logic
END
```

### 🔹 Example

👉 **Log whenever a new user is added:**

```
CREATE TRIGGER log_user_insert
ON users
AFTER INSERT
AS
BEGIN
    INSERT INTO user_logs(user_id, action)
    SELECT id, 'USER_CREATED' FROM inserted;
END;
```

### 🔹 Types of Triggers

**1. BEFORE Trigger**

- Executes before the operation

👉 Use case: validation

```
CREATE TRIGGER check_age
BEFORE INSERT ON users
FOR EACH ROW
BEGIN
    IF NEW.age < 18 THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Age must be >= 18';
    END IF;
END;
```

**2. AFTER Trigger**

- Executes after the operation

👉 Use case: logging, auditing

**3. INSTEAD OF Trigger**

- Replaces the actual operation

👉 Often used with views

### 🔹 Trigger Events

| Event  | When it fires |
| ------ | ------------- |
| INSERT | New row added |
| UPDATE | Row modified  |
| DELETE | Row removed   |

### 🔹 Special Tables (Important 🔥)

- **INSERTED** → New data
- **DELETED** → Old data

Used inside triggers to access changes.

### 🔹 Advantages

✅ Automatic execution
✅ Enforces business rules
✅ Useful for auditing/logging
✅ Maintains data integrity

### 🔹 Disadvantages

❌ Hard to debug
❌ Hidden logic (not visible in queries)
❌ Can impact performance
❌ Can create cascading issues

### 🔹 Real-World Use Cases

🛒 **E-commerce**

- Auto-update inventory after order
  🏦 **Banking**
- Log every transaction change
  🔐 **Security**
- Track login attempts or suspicious changes

### 🔹 Trigger vs Stored Procedure vs View

| Feature      | Trigger           | Stored Procedure | View             |
| ------------ | ----------------- | ---------------- | ---------------- |
| Execution    | Automatic         | Manual           | Query time       |
| Purpose      | Event-based logic | Reusable logic   | Data abstraction |
| Input params | ❌ No             | ✅ Yes           | ❌ No            |

### 🧠 Simple Analogy

- **Stored Procedure** → You press a button
- **Trigger** → Motion sensor (auto-activates)
- **View** → Saved camera angle

# 25. What is a Subquery?

A Subquery in SQL is a query inside another query.

### 🔹 Definition

A Subquery is a query nested inside a `SELECT`, `INSERT`, `UPDATE`, or `DELETE` statement.

### 🧠 Key Idea

You use a subquery when you need the result of one query to be used in another query.

### 🔹 Basic Example

```
SELECT name
FROM users
WHERE id IN (
    SELECT user_id
    FROM orders
);
```

👉 **What’s happening?**

- Inner query → gets `user_id` from `orders`
- Outer query → fetches users whose `id` matches

### 🔹 Types of Subqueries

**1. Single Row Subquery**

Returns only one row

```
SELECT name
FROM users
WHERE age > (
    SELECT AVG(age) FROM users
);
```

👉 Compare with a single value

**2. Multiple Row Subquery**

Returns multiple rows

```
SELECT name
FROM users
WHERE id IN (
    SELECT user_id FROM orders
);
```

👉 Use `IN`, `ANY`, `ALL`

**3. Correlated Subquery (Important 🔥)**

Runs once per row of the outer query

```
SELECT name
FROM users u
WHERE EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.user_id = u.id
);
```

🧠 **Think:**

Inner query depends on outer query

**4. Nested Subquery**

Subquery inside another subquery

```
SELECT name
FROM users
WHERE id IN (
    SELECT user_id
    FROM orders
    WHERE amount > (
        SELECT AVG(amount) FROM orders
    )
);
```

### 🔹 Where Can Subqueries Be Used?

✅ **In WHERE**

```
SELECT * FROM users
WHERE id IN (SELECT user_id FROM orders);
```

✅ **In SELECT**

```
SELECT name,
       (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id) AS total_orders
FROM users u;
```

✅ **In FROM**

```
SELECT avg_age
FROM (
    SELECT AVG(age) AS avg_age FROM users
) AS temp;
```

### 🔹 Subquery vs JOIN

| Feature     | Subquery           | JOIN             |
| ----------- | ------------------ | ---------------- |
| Readability | Easier (sometimes) | More structured  |
| Performance | Slower (sometimes) | Often faster     |
| Use case    | Nested logic       | Combining tables |

### 🔹 Advantages

✅ Cleaner logic for complex queries
✅ Easier to write in some cases
✅ Avoids joins when not needed

### 🔹 Disadvantages

❌ Can be slower (especially correlated subqueries)
❌ Harder to debug
❌ Less efficient than joins in many cases

### 🧠 Real-World Example

🛒 **E-commerce:**

Find users who placed orders above average amount

```
SELECT name
FROM users
WHERE id IN (
    SELECT user_id
    FROM orders
    WHERE amount > (
        SELECT AVG(amount) FROM orders
    )
);
```

### 🧠 Simple Analogy

- **Query** → One question
- **Subquery** → A question inside a question

👉 “Give me users whose orders are above average”
→ Need inner query first

# 26. UNION vs UNION ALL

UNION and UNION ALL are used to combine results from multiple SELECT queries. The key difference is how they handle duplicates.

### 🔹 UNION

- Combines results
- Removes duplicate rows
  👉 **Example:**

```
SELECT name FROM employees
UNION
SELECT name FROM customers;
```

🧠 **Behavior:**

- If John appears in both → only one John in result

### 🔹 UNION ALL

- Combines results
- Keeps duplicates
  👉 **Example:**

```c
SELECT name FROM employees
UNION ALL
SELECT name FROM customers;
```

🧠 **Behavior:**

- If John appears in both → two Johns in result

### 🔥 Key Difference

| Feature            | UNION                 | UNION ALL       |
| ------------------ | --------------------- | --------------- |
| Removes duplicates | ✅ Yes                | ❌ No           |
| Performance        | Slower                | Faster          |
| Use case           | Unique results needed | All data needed |

### 🧠 Why UNION is Slower?

- It performs an extra step:
  - Sorting / Deduplication

👉 `UNION ALL` skips this → faster 🚀

### 🔹 Rules (Important ⚠️)

Both queries must have:

- Same number of columns
- Compatible data types
- Same column order

### 🔹 Example with Multiple Columns

```
SELECT id, name FROM users
UNION
SELECT id, name FROM admins;
```

### 🔹 When to Use What?

✅ **Use UNION when:**

- You need unique results
- Duplicates are meaningless
  ✅ **Use UNION ALL when:**
- You need all records
- Performance matters
- Duplicates are valid

### 🧠 Real-World Example

🛒 **E-commerce:**

Combine users from two sources:

```
SELECT email FROM website_users
UNION ALL
SELECT email FROM mobile_users;
```

👉 Keeps duplicates → useful for analytics

### 🧠 Simple Analogy

- **UNION** → “Give me unique names”
- **UNION ALL** → “Give me everything, don’t filter anything”

### 🔥 Interview Tip

👉 Default to `UNION ALL` for performance
👉 Use `UNION` only when deduplication is required

# 27. What is a Cursor?

A Cursor in SQL is a mechanism that lets you process query results row-by-row, instead of handling the entire result set at once.

### 🔹 Definition

A Cursor is a database object used to iterate over rows one at a time.

### 🧠 Key Idea

SQL is set-based (works on all rows together), but a cursor allows procedural, row-by-row processing.

### 🔹 When Do You Use a Cursor?

Use it when:

- You need row-by-row logic
- Complex operations can’t be done with simple SQL
- You need conditional processing per row

### 🔹 Basic Workflow

- Declare cursor
- Open cursor
- Fetch rows
- Process each row
- Close cursor
- Deallocate cursor

### 🔹 Example

```
DECLARE user_cursor CURSOR FOR
SELECT id, name FROM users;

OPEN user_cursor;

DECLARE @id INT, @name VARCHAR(100);

FETCH NEXT FROM user_cursor INTO @id, @name;

WHILE @@FETCH_STATUS = 0
BEGIN
    PRINT @name;

    FETCH NEXT FROM user_cursor INTO @id, @name;
END;

CLOSE user_cursor;
DEALLOCATE user_cursor;
```

### 🧠 What’s happening?

- Cursor selects rows from `users`
- Iterates one row at a time
- Prints each name

### 🔹 Types of Cursors (Simplified)

**1. Forward-Only Cursor**

- Moves only forward
- Fastest
  **2. Scroll Cursor**
- Can move forward & backward
  **3. Static Cursor**
- Snapshot of data (doesn’t reflect changes)
  **4. Dynamic Cursor**
- Reflects real-time changes in data

### 🔹 Advantages

✅ Useful for complex row-by-row logic
✅ Helps when procedural logic is required
✅ Can handle conditional operations

### 🔹 Disadvantages (Very Important ⚠️)

❌ Slow (row-by-row = expensive)
❌ High memory usage
❌ Breaks SQL’s set-based performance advantage
❌ Harder to maintain

### 🔥 Cursor vs Set-Based Approach

❌ **Cursor (slow)**

```
-- Loop through each row
```

✅ **Set-Based (fast)**

```
UPDATE users
SET status = 'active'
WHERE last_login > NOW() - INTERVAL 30 DAY;
```

👉 Always prefer set-based queries if possible

### 🧠 Real-World Example

🏦 **Banking System**

- Apply interest per account with complex rules
- Cursor processes each account individually

### 🧠 Simple Analogy

- **Normal SQL** → “Process all rows at once”
- **Cursor** → “Loop through rows one by one”

### 🔥 Interview Tip

👉 Avoid cursors unless absolutely necessary
👉 Use:

- `JOIN`
- `GROUP BY`
- `CASE`
- Window functions

Instead of cursors whenever possible 🚀

# 28. What is a Deadlock?

A **Deadlock** in SQL/database systems is a situation where two or more transactions are stuck waiting for each other forever, and none of them can proceed.

### 🔹 Definition

A **Deadlock** occurs when transactions hold locks on resources and are waiting for each other to release those locks.

### 🧠 Simple Idea

“You’re waiting for me, and I’m waiting for you → nobody moves”

### 🔹 Classic Example

👉 **Scenario:**

Transaction 1

```
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- holds lock on row id=1

UPDATE accounts SET balance = balance + 100 WHERE id = 2;
-- waits for lock on id=2
```

Transaction 2

```
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 2;
-- holds lock on row id=2

UPDATE accounts SET balance = balance + 50 WHERE id = 1;
-- waits for lock on id=1
```

### 🚨 What happens?

- T1 locks **row 1**, waits for **row 2**
- T2 locks **row 2**, waits for **row 1**

👉 **Deadlock!** 💥

### 🔹 Visual Intuition

```
T1 → needs resource held by T2
T2 → needs resource held by T1
```

### 🔹 What Does the Database Do?

Most databases:

- Detect deadlock automatically
- Kill one transaction (rollback)

👉 Example error:

```
Deadlock detected. Transaction rolled back.
```

### 🔹 Conditions for Deadlock (Important 🔥)

All 4 must exist:

- **Mutual Exclusion** → resource is locked
- **Hold and Wait** → holding one, waiting for another
- **No Preemption** → cannot force release
- **Circular Wait** → circular dependency

### 🔹 Types of Locks Involved

- Row-level locks
- Table-level locks
- Shared vs Exclusive locks

### 🔹 How to Prevent Deadlocks

✅ **1. Access resources in same order**

```
-- Always update id=1 then id=2
```

✅ **2. Keep transactions short**

- Don’t hold locks too long
  ✅ **3. Use proper indexing**
- Reduces lock time
  ✅ **4. Avoid user interaction inside transactions**
- No delays while holding locks
  ✅ **5. Use lower isolation levels (if safe)**
- Reduces locking conflicts

### 🔹 How to Handle Deadlocks

- Catch error in application
- Retry transaction

👉 Example (pseudo):

```
try {
  runTransaction();
} catch (deadlock) {
  retry();
}
```

### 🔹 Deadlock vs Blocking

| Feature    | Deadlock     | Blocking             |
| ---------- | ------------ | -------------------- |
| Waiting    | Circular     | One-way              |
| Resolution | DB kills one | Waits until released |
| Severity   | Critical     | Normal               |

### 🧠 Real-World Example

🏦 **Banking**

- Two transfers happening at same time
- Each locks different accounts
- Ends up waiting → deadlock

### 🧠 Simple Analogy

Two people trying to cross a narrow bridge:

- Person A waits for B
- Person B waits for A

👉 Neither moves → deadlock 🚫

### 🔥 Interview Tip

👉 Deadlocks are not bugs, they are expected behavior in concurrent systems
👉 Your job is to:

- Minimize them
- Handle them gracefully

# 29. What is Database Sharding?

Database Sharding is a technique used to split a large database into smaller, more manageable pieces (called shards) and distribute them across multiple servers.

### 🔹 Definition

Sharding = horizontal partitioning of data across multiple databases/servers.

### 🧠 Key Idea

Instead of storing all data in one database → distribute it across many databases

### 🔹 Why Do We Need Sharding?

As your system grows:

- 🚫 Single DB becomes slow
- 🚫 Storage limits hit
- 🚫 High traffic overloads server

👉 Sharding helps you scale horizontally

### 🔹 How Sharding Works

You split data based on a shard key

👉 Example: Users Table
| User ID | Stored In |
| --------- | --------- |
| 1–1000 | Shard 1 |
| 1001–2000 | Shard 2 |
| 2001–3000 | Shard 3 |

### 🔹 Types of Sharding

**1. Range-Based Sharding**

Split based on ranges

```
Shard 1 → IDs 1–1000
Shard 2 → IDs 1001–2000
```

✅ Simple
❌ Can cause uneven load (hotspots)

**2. Hash-Based Sharding**

Use a hash function

```
shard = hash(user_id) % 3
```

✅ Even distribution
❌ Hard to query ranges

**3. Directory-Based Sharding**

Use a lookup table

```
user_id → shard mapping stored separately
```

✅ Flexible
❌ Extra lookup overhead

### 🔹 Architecture

```
App → Shard Router → Multiple Databases
                      ├── Shard 1
                      ├── Shard 2
                      └── Shard 3
```

### 🔹 Advantages

✅ Horizontal scaling 🚀
✅ Better performance
✅ Handles large datasets
✅ Fault isolation (one shard fails ≠ whole system down)

### 🔹 Disadvantages

❌ Complex to design
❌ Hard joins across shards
❌ Data rebalancing is difficult
❌ Requires good shard key selection

### 🔹 Sharding vs Partitioning

| Feature    | Sharding       | Partitioning   |
| ---------- | -------------- | -------------- |
| Level      | Across servers | Within same DB |
| Scaling    | Horizontal     | Vertical       |
| Complexity | High           | Low            |

### 🔹 Real-World Examples

🌐 **Social Media**

- Users split across shards by user_id
  🛒 **E-commerce**
- Orders distributed by region or user
  🎮 **Gaming**
- Players distributed across servers

### 🔹 Choosing a Good Shard Key (Very Important 🔥)

A good shard key should:

- Evenly distribute data
- Avoid hotspots
- Be frequently used in queries

👉 Bad Example:

```
Shard by country → India shard overloaded 😅
```

### 🔹 Sharding vs Replication

| Feature | Sharding            | Replication                |
| ------- | ------------------- | -------------------------- |
| Purpose | Scale writes & data | Scale reads & availability |
| Data    | Split               | Same copy                  |

### 🧠 Simple Analogy

- Single DB → One big library 📚
- Sharding → Many smaller libraries across cities

### 🔥 Interview Insight

👉 Sharding is used by large systems like:

- Facebook
- Instagram
- Amazon

👉 It’s a last resort scaling technique (after indexing, caching, replication)

# 30. What is Replication?

Database Replication is the process of copying and maintaining the same data across multiple database servers.

### 🔹 Definition

Replication = keeping multiple copies of the same database in sync across different machines.

### 🧠 Key Idea

Instead of splitting data (like sharding), replication duplicates data for reliability and performance.

### 🔹 Why Use Replication?

- 🚀 Improve read performance
- 🔒 Increase availability
- 🛡️ Provide fault tolerance
- 🌍 Enable geo-distribution

### 🔹 How It Works

```
        (Writes)
          ↓
     Primary DB
      /      \
(Read)      (Read)
Replica 1   Replica 2
```

- **Primary (Master)** → Handles writes
- **Replicas (Slaves)** → Handle reads

### 🔹 Types of Replication

**1. Master-Slave (Primary-Replica)**

- One primary database
- Multiple read replicas
  ✅ Flow:
- Writes → Primary
- Reads → Replicas
  **2. Master-Master (Multi-Master)**
- Multiple nodes can read & write
  ⚠️ Challenge:
- Conflict resolution (same data updated in different nodes)
  **3. Synchronous Replication**
- Data is written to all replicas before success

✅ Strong consistency
❌ Slower performance

**4. Asynchronous Replication**

- Primary writes first
- Replicas update later

✅ Fast
❌ Possible replication lag

### 🔹 Replication Lag (Important 🔥)

Delay between primary and replicas

👉 Example:

User updates profile
Reads from replica → old data 😬

### 🔹 Advantages

✅ High availability
✅ Load balancing (read scaling)
✅ Data backup & redundancy
✅ Disaster recovery

### 🔹 Disadvantages

❌ Data inconsistency (lag)
❌ Complex setup
❌ Write bottleneck (in single primary)

### 🔹 Replication vs Sharding

| Feature    | Replication                   | Sharding                  |
| ---------- | ----------------------------- | ------------------------- |
| Data       | Same copy                     | Split data                |
| Purpose    | Read scaling, fault tolerance | Write scaling, large data |
| Complexity | Medium                        | High                      |

### 🔹 Real-World Usage

- 🌐 Web apps → read-heavy traffic
- 🛒 E-commerce → product catalog reads
- 📱 Social apps → timelines & feeds

Used by companies like:

- Netflix
- Twitter
- Amazon

### 🔹 Common Architecture Pattern

```
Client → Load Balancer
           ↓
   ┌─────────────┐
   │   Primary   │  (writes)
   └─────────────┘
      ↓    ↓
 Replica  Replica
 (reads)  (reads)
```

### 🔹 Simple Analogy

- **Replication** → Making multiple photocopies of the same book 📚
- **Sharding** → Splitting the book into parts across libraries

### 🔥 Interview Insight

👉 Replication is usually combined with:

- Caching (Redis)
- Sharding
- Load balancing

👉 Most systems:

- Use replication first
- Add sharding later when scaling writes
