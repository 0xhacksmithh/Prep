# 41. What is Pessimistic Locking?

Pessimistic Locking is a concurrency control technique where a system locks a resource before accessing it, assuming that conflicts are likely.

“Better to lock now than deal with conflicts later.”

### 🔹 Core Idea

When one user is working on a piece of data:

- 🔒 Others are blocked from modifying (or sometimes even reading) it
- Lock is released only after the transaction completes

### 🔧 How It Works

**Step-by-step:**

- Transaction starts
- Data is locked
- Other transactions must wait
- Update happens
- Lock is released
  ###- 📦 Example

Imagine a bank account:

- User A starts transaction → locks account 🔒
- User B tries to update → ⏳ must wait
- User A finishes → lock released ✅
- User B proceeds

👉 Ensures no conflicting updates happen at all

### 🔁 SQL Example

```
SELECT * FROM users WHERE id = 1 FOR UPDATE;
```

👉 This locks the row until the transaction ends.

### 🔥 Why It’s “Pessimistic”

Because it assumes:

- “Conflicts WILL happen, so prevent them upfront.”

### ⚖️ Pessimistic vs Optimistic Locking

| Feature           | Pessimistic Locking     | Optimistic Locking        |
| ----------------- | ----------------------- | ------------------------- |
| Locking           | Yes (before access)     | No (check at update time) |
| Performance       | Lower (blocking)        | Higher                    |
| Conflict handling | Prevented               | Detected later            |
| Use case          | High contention systems | Low contention systems    |

### 🧠 Where It’s Used

- Traditional relational databases like MySQL and PostgreSQL
- Financial systems (banking, payments)
- Inventory management (prevent overselling)

### 🚀 When to Use Pessimistic Locking

Use it when:

- Data conflicts are very common
- You need strong consistency
- You cannot afford retries

Avoid when:

- High scalability is required
- Long-running transactions (can cause blocking issues)

### ⚠️ Downsides

- ❌ Reduced concurrency (others must wait)
- ❌ Risk of deadlocks
- ❌ Slower performance under load

### 🧩 Real-World Analogy

Think of a hotel room booking system (offline):

- You go to reception → they block the room
- No one else can book it until you finish

👉 That’s pessimistic locking.

### 🔗 Connection to System Design

- Works well with ACID-compliant systems
- Opposite philosophy of BASE systems
- Common in monolithic architectures

# 42. What is MVCC (Multi-Version Concurrency Control)?

**MVCC (Multi-Version Concurrency Control)** is a database concurrency technique where multiple versions of the same data are maintained, so that reads don’t block writes and writes don’t block reads.

Instead of locking data, MVCC lets transactions see a snapshot of data.

### 🔹 Core Idea

“Don’t lock the row — create a new version of it.”

### 🔧 How It Works

Each row has hidden metadata like:

- `created_version` (or transaction ID)
- `deleted_version` (optional)
  **Step-by-step:**
- Transaction A reads data → sees version 1
- Transaction B updates same row → creates version 2
- Transaction A still sees version 1 (consistent snapshot)
- New transactions see version 2

👉 Multiple versions coexist until old ones are cleaned up.

### 📦 Example

| ID  | Name | Version |
| --- | ---- | ------- |
| 1   | John | v1      |

**Scenario:**

- T1 reads → John (v1)
- T2 updates → John Updated (v2)

Now:

- T1 still sees → v1 👀
- New transactions see → v2 👀

✔ No blocking
✔ No conflicts for reads

### 🧠 Key Concept: Snapshot Isolation

Each transaction works with a snapshot of the database at a specific time.

👉 This is why MVCC is often associated with:

- **Snapshot Isolation**
- **Repeatable Reads**

### 🔥 Why MVCC is Powerful

✅ No read locks needed
✅ High concurrency
✅ Better performance in read-heavy systems

### ⚖️ MVCC vs Locking

| Feature        | MVCC      | Pessimistic Locking |
| -------------- | --------- | ------------------- |
| Read Blocking  | ❌ No     | ✅ Yes              |
| Write Blocking | Sometimes | Yes                 |
| Performance    | High      | Lower               |
| Complexity     | Higher    | Simpler             |

### 🧠 Where It’s Used

- - PostgreSQL (pure MVCC)
- - MySQL (InnoDB engine)
- - Oracle Database

### ⚠️ Trade-offs

- ❌ More storage (multiple versions)
- ❌ Needs cleanup (VACUUM / garbage collection)
- ❌ Complex implementation

### 🧩 Real-World Analogy

Think of Google Docs version history:

- You open a document → see a snapshot
- Someone edits → new version created
- You still see your version until refresh

👉 That’s MVCC in action.

### 🔗 How It Connects to Other Concepts

- Works well with ACID systems
- Reduces need for pessimistic locking
- Complements optimistic locking in some cases
- Helps achieve high concurrency without sacrificing consistency

### 🚀 When to Use / Benefit from MVCC

MVCC is ideal when:

- System is read-heavy
- You want high concurrency
- You need consistent reads without blocking

# 43. What is Query Optimization?

**Query Optimization** is the process of improving a database query so that it runs faster and uses fewer resources (CPU, memory, disk I/O).

Same result, but **more efficient execution**.

### 🔹 Core Idea

When you write a query, the database doesn’t execute it directly.
It first creates an execution plan (a strategy).

👉 Query optimization = choosing the best execution plan

### 🔧 How It Works Internally

Databases like PostgreSQL or MySQL have a Query Optimizer.

**Steps:**

- Parse SQL → understand query
- Generate multiple execution plans
- Estimate cost (time, I/O, CPU)
- Pick the lowest-cost plan

### 📦 Example

**Query:**

```
SELECT * FROM users WHERE email = 'test@example.com';
```

**Two possible strategies:**

- Scan entire table ❌ (slow)
- Use index on email ✅ (fast)

👉 Optimizer chooses the index scan.

### 🔥 Key Techniques in Query Optimization

**1. Indexing**

- Speeds up lookups
- Example: B-tree index on columns

👉 Without index → full table scan
👉 With index → direct lookup

**2. Query Rewriting**

Optimizer may rewrite queries internally.

Example:

```
WHERE age > 18 AND age > 10
```

👉 Simplified to:

```
WHERE age > 18
```

**3. Join Optimization**

Choosing the best join method:

- Nested Loop
- Hash Join
- Merge Join
  **4. Predicate Pushdown**

Filters applied as early as possible to reduce data size.

**5. Projection Optimization**

Fetch only required columns:

```
SELECT name  -- ✅ better
FROM users;
```

instead of:

```
SELECT *     -- ❌ unnecessary data
```

### ⚖️ Cost-Based vs Rule-Based Optimization

| Type                | Description                          |
| ------------------- | ------------------------------------ |
| Rule-Based          | Uses predefined rules                |
| Cost-Based (modern) | Chooses plan based on estimated cost |

👉 Most modern DBs use cost-based optimization

### 🧠 Why It Matters

- 🚀 Faster queries
- 💸 Lower infrastructure cost
- 📈 Better scalability
- 🔥 Critical for large datasets

### ⚠️ Common Mistakes

- ❌ Missing indexes
- ❌ Using SELECT \*
- ❌ Unnecessary joins
- ❌ Functions on indexed columns (WHERE LOWER(email) = ...)
- ❌ Not analyzing execution plans

### 🔍 Tools to Analyze Queries

- `EXPLAIN` / `EXPLAIN ANALYZE`
- Query execution plans
- Performance monitoring tools

👉 Example:

```
EXPLAIN SELECT * FROM users;
```

### 🧩 Real-World Analogy

Think of Google Maps:

- Many routes to destination
- It picks the fastest one based on traffic

👉 Query optimizer = Google Maps for your SQL

### 🔗 Where It’s Critical

- Large-scale systems (millions of rows)
- Data analytics platforms
- Backend APIs serving real-time requests

### 🚀 When You Should Care

Always — but especially when:

- Queries become slow
- Tables grow large
- System starts scaling

# 44. What is a Covering Index?

A Covering Index is an index that contains all the columns needed to satisfy a query, so the database doesn’t need to read the actual table at all.

“Everything the query needs is already inside the index.”

### 🔹 Core Idea

Normally:

- Index → find row location
- Table → fetch actual data

👉 With a covering index:

- Index → find + return data ✅
- Table access → ❌ NOT needed

### 📦 Example

**Table:**

```
users(id, name, email, age)
```

**Query:**

```
SELECT name, email FROM users WHERE age = 25;
```

❌ **Without Covering Index**

Index on `age` only:

- Use index → find rows
- Go to table → fetch `name`, `email`

👉 Extra I/O (slow)

✅ **With Covering Index**

Index:

```
CREATE INDEX idx_users_age_name_email
ON users(age, name, email);
```

Now:

- Index has `age`, `name`, `email`
- Query is fully satisfied from index

👉 No table lookup → much faster

### 🔥 Why It’s Fast

- Avoids table access (heap lookup)
- Reduces disk I/O
- Improves cache efficiency

### 🧠 How Databases Use It

Databases like MySQL and PostgreSQL call this:

- Index-only scan (PostgreSQL)
- Covering index (MySQL terminology)

### ⚖️ When It Works Best

Covering indexes are ideal when:

- Query is read-heavy
- You select few specific columns
- Same query runs frequently

### ⚠️ Trade-offs

- ❌ Larger index size
- ❌ Slower writes (more data to maintain)
- ❌ Too many indexes → performance degradation

### 🧩 Real-World Analogy

Think of an index at the back of a book:

- Normal index → tells you page number → you open page 📖
- Covering index → already contains the answer → no need to open book 📘

### 🔍 How to Check

Use:

```c
EXPLAIN SELECT name, email FROM users WHERE age = 25;
```

👉 Look for:

- “Using index” (MySQL)
- “Index Only Scan” (PostgreSQL)

### 🚀 Pro Tip

Design indexes based on:

- `WHERE` clause columns first
- Then `SELECT` columns

👉 This maximizes chances of creating a covering index.

# 45. What is Database Partitioning?

Database Partitioning is the technique of splitting a large table into smaller, more manageable pieces (partitions) while still treating it as a single logical table.

“Divide big data into chunks so queries run faster and systems scale better.”

### 🔹 Core Idea

Instead of one huge table:

```
users (100 million rows)
```

👉 You split it into partitions:

```
users_2023
users_2024
users_2025
```

But to the application, it still looks like:

```
SELECT * FROM users;
```

### 🔧 How It Works

The database decides which partition to query based on a rule.

👉 This is called **Partition Pruning**:

- Only relevant partitions are scanned
- Others are ignored → 🚀 faster queries

### 📦 Types of Partitioning

**1. Range Partitioning**

Split based on value ranges.

```
PARTITION BY RANGE (created_at)
```

Example:

- 2023 data → Partition A
- 2024 data → Partition B

✔ Best for time-series data

**2. List Partitioning**

Split based on specific values.

```
PARTITION BY LIST (country)
```

Example:

- India → Partition A
- USA → Partition B
  **3. Hash Partitioning**

Distribute data evenly using a hash function.

```
PARTITION BY HASH (user_id)
```

✔ Good for load balancing

**4. Composite Partitioning**

Combination of multiple strategies.

Example:

- Range (date) + Hash (user_id)

### 🔥 Why Partitioning is Powerful

✅ **Faster Queries**

- Only scan relevant partitions

✅ **Better Maintenance**

- Drop old partitions easily
- Backup per partition
  ✅ **Improved Performance**
- Smaller indexes
- Parallel processing

### ⚖️ Partitioning vs Sharding

| Feature      | Partitioning        | Sharding                  |
| ------------ | ------------------- | ------------------------- |
| Scope        | Within one database | Across multiple databases |
| Transparency | Handled by DB       | Handled by application    |
| Complexity   | Lower               | Higher                    |

👉 Partitioning = **vertical scaling aid**
👉 Sharding = **horizontal scaling strategy**

### 🧠 Where It’s Used

- PostgreSQL (native partitioning)
- MySQL
- Data warehouses, analytics systems

### ⚠️ Trade-offs

- ❌ Complex setup
- ❌ Poor partition key choice → bad performance
- ❌ Cross-partition queries can be slower

### 🧩 Real-World Analogy

Think of a library:

- Instead of one giant shelf 📚
- Books are divided by year / category

👉 You go directly to the right section → faster search

### 🚀 When to Use Partitioning

Use it when:

- Tables are very large (millions/billions of rows)
- Queries filter on a specific column (date, region, id)
- You need faster reads and easier maintenance

### 🔗 Related Concepts

- Works great with indexes
- Often combined with sharding
- Important in data-intensive system design

# 46. What is a Materialized View?

A Materialized View is a database object that stores the result of a query physically, instead of computing it every time you run the query.

“Precompute and store the result → faster reads.”

### 🔹 Core Idea

**Normal View:**

- Just a saved SQL query
- Runs every time you query it ❌ (can be slow)
  **Materialized View:**
- Query result is stored on disk ✅
- Reads are fast, like a table

### 📦 Example

**Query:**

```
SELECT customer_id, COUNT(*) AS total_orders
FROM orders
GROUP BY customer_id;
```

❌ **Normal View**

Every request:

- Recalculate aggregation → slow
  ✅ **Materialized View**

```
CREATE MATERIALIZED VIEW customer_order_summary AS
SELECT customer_id, COUNT(*) AS total_orders
FROM orders
GROUP BY customer_id;
```

👉 Result is stored:

```
customer_id | total_orders
------------|--------------
101         | 25
102         | 10
```

Now:

```
SELECT * FROM customer_order_summary;
```

👉 Instant ⚡

### 🔄 Refreshing Materialized Views

Since data changes, materialized views can become stale.

**Refresh options:**

- Manual Refresh

```
REFRESH MATERIALIZED VIEW customer_order_summary;
```

- Scheduled Refresh
  - Cron jobs
  - Periodic updates
- Incremental Refresh (advanced)
  - Only update changed data

### 🔥 Why Use It

- 🚀 Faster query performance
- 📊 Great for aggregations (COUNT, SUM, JOINs)
- 📈 Useful in analytics & reporting

### 🧠 Where It’s Used

- PostgreSQL (native support)
- Oracle Database
- Data warehouses (OLAP systems)

### ⚖️ Materialized View vs Normal View

| Feature     | Materialized View | Normal View        |
| ----------- | ----------------- | ------------------ |
| Storage     | Stores data       | No storage         |
| Performance | Fast              | Slower             |
| Freshness   | Can be stale      | Always fresh       |
| Use case    | Heavy queries     | Simple abstraction |

### ⚠️ Trade-offs

- ❌ Uses storage space
- ❌ Needs refresh strategy
- ❌ Data may be outdated

### 🧩 Real-World Analogy

Think of a monthly sales report PDF:

- You generate it once 📄
- Everyone reads it quickly
- But it doesn’t update automatically

👉 That’s a materialized view.

### 🚀 When to Use

Use materialized views when:

- Queries are expensive (joins, aggregations)
- Data doesn’t need to be real-time
- You need fast dashboards or reports

### 🔗 Related Concepts

- Works well with query optimization
- Often combined with indexes
- Used in analytics pipelines

# 47. What is Write-Ahead Logging (WAL)?

**Write-Ahead Logging (WAL)** is a technique used by databases to ensure data durability and crash recovery.

“Before changing the actual data, first write the change to a log.”

### 🔹 Core Idea

Instead of directly updating the database:

- ✍️ Write the change to a log file (WAL)
- 💾 Then apply it to the actual data

👉 If a crash happens, the system can replay the log and recover.

### 🔧 How It Works

Step-by-step:

- Transaction starts
- Changes are written to WAL log
- WAL is flushed to disk (important!)
- Actual data pages are updated later
- Transaction is committed

### 📦 Example

Imagine updating a user balance:

```
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
```

**What WAL does:**

- Log entry:

```
"User 1: -100"
```

- Save log to disk ✅
- Update database ❗
  **Crash Scenario**
  If system crashes after step 2 but before step 3:

- Database may not be updated ❌
- But WAL has the change ✅

👉 On restart → **replay log** → **recover data**

### 🔥 Why WAL is Important

✅ **Durability (ACID)**

Ensures committed data is not lost

✅ **Crash Recovery**

System can rebuild state from logs

✅ **Performance Boost**

- Sequential log writes (fast)
- Batch disk operations

### 🧠 Where It’s Used

- PostgreSQL (core mechanism)
- MySQL (InnoDB redo logs)
- SQLite

### ⚖️ WAL vs Direct Write

| Feature        | WAL                        | Direct Write           |
| -------------- | -------------------------- | ---------------------- |
| Safety         | High (recoverable)         | Low                    |
| Performance    | Better (sequential writes) | Slower (random writes) |
| Crash Recovery | Easy                       | Hard                   |

### 🔁 WAL + Checkpointing

WAL doesn’t grow forever.

👉 Databases periodically do checkpointing:

- Flush data to disk
- Clear old logs

### 🧩 Real-World Analogy

Think of writing in a notebook before updating a ledger:

- Write transaction in notebook 📓
- Then update official ledger 📘

If ledger update fails → notebook still has record ✔

👉 WAL = notebook

### 🔗 Related Concepts

- Works with **ACID properties (Durability)**
- Supports **replication** (log shipping)
- Helps in **point-in-time recovery**

### 🚀 When It Matters Most

- Financial systems 💳
- Critical applications 🔥
- Any system where **data loss is unacceptable**

# 48. What is the N+1 Query Problem?

The **N+1 Query Problem** is a performance issue where an application executes:

- 1 query to fetch a list of items + N additional queries (one per item)

👉 Result: **too many database calls → slow performance**

### 🔹 Core Idea

Instead of fetching related data in one optimized query, the system fetches it one-by-one in a loop.

### 📦 Example

**Scenario:**

You want to fetch users and their orders.

❌ **Bad (N+1 Problem)**

```c
// 1 query
const users = await getUsers();

// N queries (for each user)
for (const user of users) {
  user.orders = await getOrdersByUserId(user.id);
}
```

👉 If:

- 100 users → 1 + 100 = 101 queries
  ✅ **Good (Optimized)**

```c
SELECT users.*, orders.*
FROM users
LEFT JOIN orders ON users.id = orders.user_id;
```

👉 Only **1 query instead of 101** 🚀

### 🔥 Why It’s a Problem

- ❌ Too many DB round trips
- ❌ High latency
- ❌ Increased load on database
- ❌ Poor scalability

### 🧠 Where It Commonly Happens

- ORMs like Hibernate
- ORMs like Sequelize
- GraphQL resolvers (nested queries)

### 🔧 Solutions

**1. Eager Loading (JOINs)**

Fetch related data in one query.

```
User.findAll({ include: Orders });
```

**2. Batch Loading**

Fetch all related data at once.

```
SELECT * FROM orders WHERE user_id IN (1,2,3,4,...);
```

**3. DataLoader Pattern (GraphQL)**

Batch + cache queries efficiently.

**4. Caching**

Use Redis or in-memory caching to avoid repeated queries.

### ⚖️ Lazy Loading vs Eager Loading

| Feature     | Lazy Loading (N+1 risk) | Eager Loading  |
| ----------- | ----------------------- | -------------- |
| Queries     | Many                    | Few            |
| Performance | Slow                    | Fast           |
| Control     | More dynamic            | More optimized |

### 🧩 Real-World Analogy

Think of ordering food:

- ❌ N+1 problem:
  - You order 1 pizza 🍕
  - Then separately order toppings one by one 😅
- ✅ Optimized:
  - You order pizza with all toppings in one go ✔

### 🔍 How to Detect It

- Logs show many repeated queries
- Performance slows with more data
- Use profiling tools / query logs

### 🚀 When It Becomes Critical

- Large datasets (100s–1000s of rows)
- APIs serving lists (feeds, dashboards)
- GraphQL nested queries

### 🔗 Related Concepts

- Query Optimization
- Joins & Indexing
- Caching strategies

# 49. What is SQL Injection?

**SQL Injection (SQLi)** is a security vulnerability where an attacker injects malicious SQL code into a query to manipulate the database.

- “When user input is treated as SQL instead of data.”

### 🔹 Core Idea

If your application builds SQL queries using unsanitized user input, attackers can:

- Bypass authentication
- Read sensitive data
- Modify or delete data

### 📦 Example (Vulnerable Code)

```
const query = `SELECT * FROM users WHERE email = '${email}' AND password = '${password}'`;
```

❌ **Attack Input**

User enters:

```
email: anything' OR '1'='1
password: anything
```

**Resulting Query**

```
SELECT * FROM users
WHERE email = 'anything' OR '1'='1'
AND password = 'anything';
```

👉 `'1'='1'` is always true → login bypass 😱

### 🔥 Types of SQL Injection

**1. Authentication Bypass**

- Skip login checks
  **2. Data Extraction**

```
UNION SELECT username, password FROM users;
```

**3. Data Modification**

```
DROP TABLE users;
```

### 🧠 Where It Happens

- Login forms
- Search fields
- URL query params
- APIs

### ⚠️ Why It’s Dangerous

- 🔓 Unauthorized access
- 💣 Data loss or corruption
- 🕵️ Sensitive data leaks

### 🔧 How to Prevent SQL Injection

✅ **1. Use Prepared Statements (Best)**

```
const query = "SELECT * FROM users WHERE email = ? AND password = ?";
db.execute(query, [email, password]);
```

👉 Input is treated as data, not code

✅ **2. Use ORM/Query Builders**

Libraries like:

- Sequelize
- Hibernate

Automatically handle parameterization.

✅ **3. Input Validation & Sanitization**

- Reject unexpected input
- Use strict formats (email, numbers)
  ✅ **4. Least Privilege**
- DB user should not have full access
- Avoid DROP, DELETE permissions if not needed
  ✅ **5. Use Stored Procedures (carefully)**

### 🧩 Real-World Analogy

Think of a form submission:

- ❌ Unsafe:
  - You directly paste user text into a command
- ✅ Safe:
  - You treat user input as plain data, not instructions

### 🔗 Related Concepts

- Web security (OWASP Top 10)
- Authentication systems
- Input validation

### 🚀 When It Matters

**Always** — even a small vulnerability can:

- Expose entire databases
- Break production systems

### 🧠 Quick Rule

- ❗ Never trust user input
- ❗ Always parameterize queries

# 50. How to Optimize Slow Queries?

Optimizing slow queries is a mix of diagnosing the bottleneck and applying the right fix **(indexing, rewriting, or design changes)**.

“Don’t guess — measure, analyze, then optimize.”

### 🔍 Step 1: Identify the Slow Query

Use tools like:

```
EXPLAIN ANALYZE SELECT * FROM users;
```

Databases like PostgreSQL and MySQL show:

- Execution plan
- Time taken
- Rows scanned

👉 Look for:

- Full table scans ❌
- Large row counts ❌
- Expensive joins ❌

### 🔧 Step 2: Use Proper Indexing

✅ Add Indexes on:

- `WHERE` conditions
- `JOIN` columns
- `ORDER BY` / `GROUP BY`

```
CREATE INDEX idx_users_email ON users(email);
```

👉 Avoid:

- Over-indexing (hurts writes)
- Indexing low-selectivity columns (e.g., gender)

### ⚡ Step 3: Avoid SELECT \*

```
-- ❌ Bad
SELECT * FROM users;

-- ✅ Good
SELECT id, name FROM users;
```

👉 Reduces data transfer + enables covering index

### 🔁 Step 4: Fix N+1 Query Problem

Instead of:

- Multiple queries in loop ❌

Use:

- JOINs or batching ✅

👉 (See: N+1 Query Problem)

### 🔗 Step 5: Optimize Joins

- Ensure join columns are indexed
- Choose correct join type
- Avoid unnecessary joins

👉 Example:

```c
SELECT u.name, o.amount
FROM users u
JOIN orders o ON u.id = o.user_id;
```

### 📉 Step 6: Reduce Data Early (Filter First)

```
-- ❌ Bad
SELECT * FROM orders;

-- ✅ Good
SELECT * FROM orders WHERE status = 'completed';
```

👉 This is predicate pushdown

### 🧠 Step 7: Use Proper Query Patterns

❌ **Avoid:**

```
WHERE LOWER(email) = 'test@example.com';
```

👉 Breaks index usage

✅ **Use:**

```
WHERE email = 'test@example.com';
```

### 📦 Step 8: Use Covering Index

If query only needs a few columns:

```
CREATE INDEX idx_users_age_name_email
ON users(age, name, email);
```

👉 Avoids table lookup → faster

### 🔄 Step 9: Use Pagination

```
SELECT * FROM users LIMIT 10 OFFSET 0;
```

👉 Prevents loading massive datasets

### 🧊 Step 10: Cache Frequently Used Data

- Use Redis / in-memory cache
- Avoid hitting DB repeatedly

### 🧱 Step 11: Use Materialized Views

For heavy aggregations:

- Precompute results
- Serve instantly

### ⚙️ Step 12: Partition Large Tables

Split large tables:

- By date
- By region

👉 Query only relevant partitions

### 🔥 Step 13: Optimize Write Patterns

- Batch inserts
- Avoid frequent commits
- Use bulk operations

### 🧠 Step 14: Monitor & Profile

- Query logs
- Slow query logs
- Performance dashboards

### ⚠️ Common Mistakes

- ❌ Missing indexes
- ❌ Wrong index order
- ❌ Too many joins
- ❌ N+1 queries
- ❌ Ignoring execution plan

### 🧩 Real-World Optimization Flow

- Detect slow query
- Run EXPLAIN ANALYZE
- Add/adjust index
- Rewrite query
- Re-test performance

### 🚀 Pro-Level Tips

- Use composite indexes wisely
- Prefer EXISTS over IN (sometimes faster)
- Use denormalization for heavy reads
- Tune DB config (memory, cache)

### 🧠 Simple Analogy

Think of a library:

- No index → search every book 📚 ❌
- With index → go directly to shelf ✅
- With summary sheet → instant answer ⚡

### 🔗 Related Concepts

- Query Optimization
- Indexing (B-tree, covering index)
- N+1 Problem
- Materialized Views
- Partitioning
